# P3 源码根因分析与修复方案

日期：2026-09-17  

## 结论

**这次确实读取了项目源码，并执行了源码级复现。结论不是“只剩 UI 证据收尾”。**

现有 A/B 两阶段提交、服务端 Action、事件账本、opaque token、revision 和候选 hash 的主干不需要推翻。阻碍 P3 收敛的主要问题是：

1. **投影/编译层越过职责，给任意未绑定 NPC 目标补写完成条件。** 这使“发生了一个有证据的目标变化”不等于“角色正确地完成了那个目标”。
2. **历史事实、审阅可引用依据、审阅输出 schema 三者不一致。** 真实历史核验被误判为无依据；玩家被放入 `npcId` 字段后又被当成剧情位置错误。
3. **错误被送到不该修复它的环节。** 审阅响应/依据目录的问题导致作者重新生成剧情，消耗有限候选次数，并可能引入新的内容错误。
4. **真实运行验收没有充分检验原 P3 的能力目标。** 两路通关不证明 C3 合作准入分化；自由策略与调查的先后关系也被放宽为“出现在不同步骤”。
5. **UI 有可复现的派发活性问题，UI 验收脚本与交接说明也存在实际冲突。** 这些必须与模型拒绝、业务拒绝分开定位。

对 `p3-live-44` 最准确的表述应是：**两条保存的 CLI 轨迹到达成功结局，但不能据此将 P3 原完成矩阵的全部规则能力判为通过。** 对 `p3-ui-live-01` 的 action 14，现有材料仍不足以指定唯一历史故障点；本报告不会将条件复现的 UI 缺陷冒充那次现场已经发生的异常。

## 二、先还原项目真正的运行架构

项目不是“模型直接改世界”的简单聊天系统。当前主干是：

```text
玩家点击当前 token，或向当前 NPC 输入自由文本
   ↓
服务端按当前状态构建 choiceMap，检查 revision / Action 释放条件
   ↓
A：performTurn → 规则结算 → 真实 Event / World / Story / pending job
   ↓ 单次 CAS
UI 得到 pending 状态，通过 ensure 派发 B
   ↓
B：准备观察者记忆 → 必要时 NPC 私下判断 → 作者候选
   ↓
compileNarrativeDraft → 结构/规则预审批 → 审阅上下文与逻辑审阅
   ↓ 合法则提交；不合法则按现有有限候选预算修订
批准的 World / Story / Event / History / choiceRegistry / bundle
   ↓ 单次 CAS
ready UI；续接槽只在玩家真实执行对应 Action 后消费
```

需要保留的正确边界：

**A 成功、B 失败不是天然设计错误。** 行动已发生，后续叙事可以失败后重试，关键是不能再执行一次行动。实际编排故障注入中，B 经过三版失败后，A 的 Event Ledger 保持不变。参见 [S10](P3_源码证据索引.html#S10)、[S18](P3_源码证据索引.html#S18)。

**持久层不是完全没有事务保障。** `sqliteGameRepository.applyState` 已经有事务、revision 与 job 条件检查、失败回滚；不能仅因一次证据导出不完整就推断世界状态和事件一定分开写坏。参见 [S19](P3_源码证据索引.html#S19)。

**正式交付不是一段台词。** `isStoryDeliveryComplete` 同时核对绑定接应人、当前物品持有者与真实成功 `item_given` 事件。续接也有实际触发条件，预写未来文本不自动成为历史。参见 [S20](P3_源码证据索引.html#S20)、[S23](P3_源码证据索引.html#S23)。

**当前披露可能影响目标、任务和下一场图，因此不能在其结构效果确定前草率冻结未来图。** `previewSceneDisclosure` 的预览存在合理原因；优化必须保留预览与正式提交的区分。参见 [S21](P3_源码证据索引.html#S21)。

所以，不建议把 A/B 合成一个跨模型等待的数据库事务，不建议让模型生成正式事件 ID，也不建议放弃当前 token/revision 保护。需要修的是这些边界之间的**语义契约**，不是先换引擎、换数据库或拆成更多服务。

## 三、根因 F1：编译器在作者没有提出时，擅自给任意目标安装完成条件

### 3.1 具体源码

`src/game/application/server/ai/narrativeDraftProjection.ts`：

- L131–162：`p3EvidenceGoalBinding`。
- L142：找 `goals.findIndex(goal => goal.status === "active" && goal.resolution === undefined)`。
- L158–160：统一补成委托人 `knows_fact` 即完成。
- L299–306：`compileNarrativeDraft` 将它附加进正式待审批 proposal。

参见 [S03](P3_源码证据索引.html#S03)。

这不是单纯的别名解析、补空数组或把局部引用转成正式 ID，而是在决定：**哪个目标应因什么条件完成。** 同时它以第一个成功调查事实、第一个未绑定 active goal 为依据，而非明确的角色目标与证据关系。

### 3.2 已执行复现

R1 从 `before:3` 的原始快照调用真实 `performTurn`，再编译原始作者响应。作者没有 `consequenceBindings`，编译结果却新增 goalOrdinal 0 的绑定；完整 proposal 与原审阅请求一致。

R5 对 action 5 做相同检查：前一个目标已绑定后，程序继续给 **goalOrdinal 1** 安装同一个 `knows_fact(npc_0, fact_dyn_4)`。

原运行在 action 6 分享之后同时完成的两个目标包括：

```text
目标 0：让沈砚在离开茶棚前选定渡口查验方式，并说明会先向谁公开结果。
目标 1：保住十二户船户的旧泊权，不让旧契在交付前被新税搅乱。
```

**收到守夜人调查报告，并不证明“十二户船户的旧泊权已经保住”。** 这里目标改变确实有事件来源，但完成条件本身不表达该目标的语义。目标归约器是在照着上游安装的条件正常运行；不能通过继续给归约器加例外修正。

### 3.3 为什么这会使验收误导开发

live checker 只需要发现与调查/分享有关的 `npc_goal_status_changed`，不要求它是**指定、语义相符、能影响后续合作的目标变化**。于是程序能制造“有目标变化”的技术正证据，却没有证明原计划的角色因果与合作体验。参见 [S04](P3_源码证据索引.html#S04)、[S05](P3_源码证据索引.html#S05)。

这是代码行为，不代表本报告推断开发者有意绕过验收。

### 3.4 修复

**删除以“第一个未绑定目标”为依据的自动补写。** 将绑定来源限定为已批准的故事能力契约或候选明确提出、经核验的绑定。投影器只解析引用、验证结构和生成合法槽位，不创造角色目标的完成含义。

若 P3 需要“委托人收到调查报告”这一机械目标，应显式建立该小目标，并绑定准确事实；长期愿望“保住旧泊权”可以保留为尚未完成的长期目标，不能拿它冒充报告接收状态。

缺少必要绑定时，返回“能力覆盖缺失”，保留失败样本。不能为了让 `goalChanged` 为真，再自动挑另一个目标。

必要回归：作者无绑定不出现额外绑定；目标数组换序不改变语义；第二次/第三次编译不继续绑定下一个目标；一次分享不能完成无关长期目标；明确绑定的小目标有正确来源事件。

## 四、根因 F2：真实发生的历史核验，进了记忆文本，却进不了审阅证明目录

### 4.1 具体源码

`narrativeExecutionChecks.ts` L37–48 把历史成功事件筛成 `item_given` / `item_obtained`，前提目录仅含当前 action、历史物品转移与已发现 fact。

`narrativeReviewRules.ts` L92–100 同样只为历史物品事件创建 `event:*` 依据。历史 `request_verification`、分享、承诺等并未获得相应的可引用前提。

参见 [S07](P3_源码证据索引.html#S07)、[S08](P3_源码证据索引.html#S08)。

### 4.2 与原记录逐项对应

private action 7 已成功执行：

```text
operation: request_verification
npcId: npc_0
factIds: [fact_dyn_4]
outcome: success
sequence: 30
```

action 10 第二版旁白回顾“再回茶棚与何九当面把这条证据认下”，是对真实历史的回顾。

但审阅该段时可选依据只有：

```text
action:private-action-10
fact:fact_0
fact:fact_1
fact:fact_2
fact:fact_3
fact:fact_dyn_4
```

历史核验事件虽出现在同次请求的来源记忆中，却不在 `prerequisiteBasisKeys` / `ruleBasis` 中。审阅器返回 `basisKey:null`，服务端随即判定：

```text
已完成前提没有规则依据：已回茶棚与何九核验守夜人证据
```

R4 使用实际 action、编译和审批上下文重建，复现了该拒绝，并得到原候选 hash `candidate_f2e095ac`。

### 4.3 根因不是记忆缺失，而是两种上下文不一致

```text
业务已完成 → 事件已保存 → 作者看得到 → 审阅正文也能看到
                                  ↓
                     审阅获准引用的目录没有它
                                  ↓
                    正确历史被退回作者重写
```

要求模型“再仔细遵守 prompt”解决不了这个问题，因为规则同时要求它不得引用目录之外的依据。

### 4.4 修复

由同一观察者权限投影建立统一的、带事件类型与时序的 evidence catalog，供作者上下文与审阅共同使用。历史核验需保留当事 NPC、事实集合、受众、事件来源和成功状态；不能只给一个不透明 ID。

已提交历史与条件续接依据必须分层：`event:*` 是已发生；`step:*` 只在相应条件槽成立。不能为解决缺项把未来步骤塞进当前历史，也不能把所有 NPC 的私密事件全量公开。

错误分类也要区分“世界中没有此事件”和“事件存在但审阅投影漏了”；后者修复上下文构建，不消耗作者修订次数。

必要回归：原 action 10 样本应能引用 action 7；删除 action 7 后同一断言必须失败；错误 NPC/事实/受众、未来事件、其他存档事件不能通过。

## 五、根因 F3：审阅器的参与者协议错误，被误判为作者的剧情错误

### 5.1 具体源码与原记录

`narrativeExecutionChecks.ts` L33–35 只建立 NPC 的位置表；L120 的提示词要求抽取“实际到场/参与关键事项的人物”，但字段是 `npcId`；L149 主要检查非空字符串；L150 直接在 NPC 表中查人。

原 private action 3 审阅响应把主角填成：

```json
{"npcId":"player_0","locationId":"loc_dyn_1"}
```

同时 `playerLocation` 已经正确表达主角位置。后续校验仍报告“参与者 player_0 的实际地点没有对应规则依据”。该记录涉及 5 个路径，public action 6 也出现同类问题。

R2 将保存的审阅响应输入实际 validator，得到这 5 个错误；仅把审阅响应中的玩家重复参与者去掉、保持所有剧情文本不变，校验不再出现这些错误。**这是定位变量的对照实验，不是建议在生产中悄悄删掉不利证据。**

### 5.2 错误进入了错误的重试层

项目已经有“同一 candidateHash 重审一次”的机制，不能说完全没有分层重试。但该机制只处理返回结构无法解析为合法 pass 的情形。

这类 `player_0` 错填通过了宽松结构检查，随后产生 candidate defect，直接送回作者。R3 实际调用 `createLiveNarrativeCandidateReview`，复现一次审阅后返回 5 个作者缺陷，而不是重审响应。

R10 在真实生成编排器中，连续注入该已记录的审阅协议故障，结果是 3 次作者生成、3 次审阅，最终 `provider_failed`，而 A 的事件账本没变。**R10 是重复故障注入，不声称历史 action 3 当时三次都失败；原轨迹后来恢复了。**

参见 [S09](P3_源码证据索引.html#S09)、[S10](P3_源码证据索引.html#S10)。

### 5.3 修复

统一参与者的类型：若字段是 NPC-only，schema 和提示词均明确排除玩家；若要支持全部角色，改用带角色类型的 entity reference，并分别核对玩家和 NPC 状态。

更重要的是将错误至少分为：

| 错误归属 | 修复对象 | 是否重写作者候选 |
| --- | --- | --- |
| 审阅引用、参与者类型、path/quote 格式错误 | 审阅响应 | 否，绑定同一 candidateHash 重审 |
| 已提交依据被投影遗漏 | 服务端上下文/证明目录 | 否 |
| 候选确实说了未执行的动作或越权事实 | 作者候选 | 是，定向修改 |
| 网络请求失败 | 对应调用 | 不等于重做业务 Action |
| 提交状态不确定 | job/revision/提交记录 | 先查，不重新执行 A |

不要把 3 候选扩大为 10 候选来掩盖分流错误。审阅重试也必须有界，计入总 HTTP 预算，不能成为无限循环。

## 六、根因 F4：live 验收检查的是事件组合，未充分检查 P3 能力的差异和因果

### 6.1 C3 要求明确，但真实 runner 没有跨路线断言

原计划 C3 要求：

> 两路至少一项后续实际 Action 的准入不同，继续两次行动后仍有可追溯后果。

`p3RouteSatisfied` L311–339 检查通关、调查见证类型、核验、交付、目标变化、回访等；`narrativeP3LiveJourney.ts` L248–275 对两条 route 的完成状态聚合，**没有比较它们实际 Action 准入**。

参见 [S02](P3_源码证据索引.html#S02)、[S05](P3_源码证据索引.html#S05)、[S06](P3_源码证据索引.html#S06)。

### 6.2 本次不是只看名字、按钮或张力

对两个 runtime 的 `before:3` 至 `before:15` 共 13 对 ready 快照：

1. 用真实 `buildChoiceMap` 计算可选行动。
2. 忽略 opaque token 的字面值及生成的 interaction ID；互动按 operation、NPC、事实与受众对应，实际准入比较还保留 dialogueAct。
3. 对每个实际提供的固定行动，从新鲜的快照副本调用真实 `performTurn`。
4. 比较是否接受及拒绝 code；不调用 provider，不串行修改原快照。

**13 对快照的行动语义与实际提交准入结果均相同。** 其中 12 对位于调查之后。完整结果见 `route-action-comparison.json`。

样本中见证 NPC 在调查前就已通过 `initial_world` 知道该事实，已记录快照也没有相应合作定义把见证差异接到准入条件上。private/public 的证据质量、见证数组、张力仍有差异，但这些差异没有在本次检查的决定点转成 C3 要求的后续实际权限差异。

结论限于这些已保存状态和已提供行动，不声称整个状态空间或所有可能自由文本未来完全相同。**但现有资料不能为 C3 的 live 验收给出通过证据。**

### 6.3 C4 的先后关系也被漏检

同一函数的策略验收写的是：

```js
next.action?.type === "investigate" && nextIndex !== index
```

不是 `nextIndex > index`，更没有验证后续行动来自该自由策略促成的当前合法选项。

原 private 记录唯一的主动调查在 action 3 / turn 4，自由策略输入在 action 5 / turn 6；最终账本没有更晚的主动调查。R12 用真实验收函数和明确标为合成的最小 steps，证明“调查 → 回访 → 自由输入”这个逆序组合也返回通过。

这不能被写成已经证明了“自由输入本身不执行调查，而是产生随后可选的调查并由玩家执行”。它只能证明这些事件曾在一条路线上出现。是否用后续核验/交付另行覆盖 C4，应有明确的策略与 Action 对应证据，不能由这个 `!==` 判断代替。

### 6.4 修复

把 C1–C8 从文档清单变成有独立证据字段的验收矩阵，至少新增：

- **C3**：同一分叉初态、明确比较点、真实合法 Action/拒绝原因差异、差异所依据的知识/见证/目标条件；继续两次行为后的因果事件。
- **C4**：策略输入序号、输入后批准的选项版本、玩家选择的对应 Action、结果事件序号；输入本身不能增加调查/交付结果。
- **C2**：指定目标与语义相符的条件，不接受任意 `npc_goal_status_changed` 充数。

不能通过提前固定正确剧情、偷偷补绑定、丢掉失败分母来让矩阵通过。能力没生成出来就是覆盖失败，应保留样本。

## 七、UI F5：第一次 ensure 未成功派发时，同一 pending job 可能永远只读不生成

### 7.1 代码链路

`CurrentGameScreen.tsx` L167–171：

```ts
if (observedPendingJobKey.current !== pendingJobKey) {
  observedPendingJobKey.current = pendingJobKey;
  const outcome = await ensureNarrative();
  if (!outcome.ok) failures++;
}
```

随后只 GET 当前状态。服务端 `performTurn` 负责 A，GET 只投影状态，正常 B 派发由 `ensureNarrativeScene` 完成。

参见 [S11](P3_源码证据索引.html#S11)、[S12](P3_源码证据索引.html#S12)、[S24](P3_源码证据索引.html#S24)。

### 7.2 条件与复现

当第一次 ensure 请求在服务端真正排队前失败，而后续 GET 仍返回同一 pending job 时：

```text
pending 已保存
→ UI 先记“见过该 job”
→ ensure 未成功派发
→ 后续同 key，不再 ensure
→ GET 不启动生成
→ 没有其他 worker 介入时一直等待
```

R11 提取并执行原文件中的实际 effect，仅替换 hook、定时器和网络 I/O，复现 **1 次 ensure，6 次 GET，没有第二次派发**。这是源码控制流单元复现，不是完整 React 渲染或浏览器 E2E。

此缺陷成立，但因为没有 `p3-ui-live-01` 的对应请求/服务日志，**不能认定历史 action 14 就是这种网络失败。**

### 7.3 修复

把“已观察”与“已确认派发”拆开。只有 ensure 成功返回已排队/已运行/已不需要时才记为已派发；失败保持可重试，采用有界退避。

重试的是同一 job 的幂等派发，不是重新发玩家 Action，不是对 `provider_failed` 自动开启新一轮付费候选。利用现有 coordinator 和 lease 防重复；超过派发重试限额后显示明确恢复入口，不保持无解释的 loading。

回归至少覆盖：首次派发未到服务端、服务端已排队但响应丢失、已运行时重复 ensure、组件卸载、持久化 pending 后 reload，以及 provider 预算已耗尽不自动开新 epoch。

## 八、UI F6：验收脚本与交接说明不是同一个执行协议

`narrativeP3UiJourney.mjs` 只有约 145 行，这里的差异不是猜测，均可直接定位。[S13](P3_源码证据索引.html#S13)

### 8.1 实际只让 private 走 UI

L45–46：非 private 直接返回 undefined。L135–138 明确写 `private:"next_ui", public:"api"`。原 P3 计划也是“至少一条实际 UI”。交接文档却要求最后补 public UI route。

这是一项范围冲突。应明确选择：沿原计划以 private UI + public API 完成，或正式升级为两条 UI 并补脚本实现。**不能把现有 public API 流称作 public UI，也不能在未确认范围时无限追逐脚本不支持的结果。**

### 8.2 同目录并不支持进程重启后续跑

L50：已有 `private.ui.json` 或 `private.ui-reviewed` 即抛 `UI_EVIDENCE_ALREADY_EXISTS`。当前 expected command 与等待 Promise 在内存中，没有从旧证据恢复的路径。

原进程仍活着时可以继续点击；**进程已退出后，“存档还在”不等于“验收 runner 可以从同目录续跑”。** R8 复现了已有证据文件即拒绝的行为。

短期应明确使用新 runId 完整执行，而不是覆盖旧证据。需要续跑时，补持久化 runner checkpoint：协议/代码/路线/步骤/expected command/revision/预算/刷新状态，以及最后已提交行动。恢复必须先与存档对账。

### 8.3 结局后刷新不满足当前脚本的刷新证明

L88–93 只捕获：非首次首页导航、已有成功 browser action、叙事 ready，且 `worldState.ending === null`。

L117 最终要求 `refreshVerified`。因此应在**中途 ready、尚未结局**时刷新。若从未中途刷新，只在最终结算后刷新，不会生成合格的 proof，最后仍可报 `UI_REFRESH_NOT_EXERCISED`。

交接文档“完成 action 14、最终结算和刷新复核”的措辞不足以表达这一条件；执行清单必须写明时点，而不能只写“刷新过”。

### 8.4 当前合法 token 也可能被验收 gate 拒绝

L27–29 不仅检查生产合法性，还要求提交的 revision 和 interaction 与 runner 预选的 expected command **完全一致**。R9 用当下两个合法调查 token，等待其中一个后提交另一个，复现了在进入业务 `performTurn` 前就被 gate 拒绝。

这不是建议绕过 gate，而是要求日志明确区分：验收步骤不匹配、生产 token 失效、业务规则拒绝、候选失败。否则会一直围绕 token 字符串猜测，却没有发现拒绝来自验收层。

`descriptors.ts` L163–168 用“回访原委托人”“实际告知”“调查证据”三个精确包含条件激活 P3 闭环。`approveNarrativeBundle.ts` 又使用另一组中文/字段字符串正则判断主动调查需求。参见 [S14](P3_源码证据索引.html#S14)、[S15](P3_源码证据索引.html#S15)。

## 十、为什么已有不少测试通过，真实 API 仍反复？

不是简单“测试数量不够”。目前有两种覆盖落差。

**第一，离线审阅 fixture 有意只测试协议与传输。** `narrativeReviewFixture.testutil.ts` L11–18 返回 `playerLocation:unchanged`，参与者、转移和已完成前提均为空。它不会触发真实响应中非空参与者和历史前提的组合错误。该 fixture 的用途合理，但不能替代保存的真实审阅响应回归。[S16](P3_源码证据索引.html#S16)

**第二，离线构造的 P3 样本已经包含正确的见证/目标/合作条件，不代表真实生成的样本也生成了这些条件。** 离线 P3 测试确实有分化测试；live 的 completed checker 却没有强制检验相同能力，所以两者可以同时“绿灯”而真实样本缺少 C3。

应保留现有测试，再加入跨边界的真实失败 fixture：原请求、作者输出、编译产物、审阅输出、最终分类均保存；测试既检查能否通过，也检查**通过时到底证明了什么**。

## 十三、是否需要分阶段生成的架构改造？

**P3 近期不需要推翻架构；中期可以收紧“结构效果 → 图 → 文本”的顺序。**

保留：纯规则、observer 权限、正式事件、A/B 独立、候选 hash、有限预算、CAS。

收紧：绑定来源、历史证明目录、类型协议、修复归属、跨路线验收、UI 派发/runner 恢复。

## 最终判断

**问题不是项目完全没有架构，而是部分实现和验收已经偏离了架构本来想守住的边界。** 最直接的修复抓手，是停止编译器擅自补角色目标、补齐历史审阅依据、纠正错误分流、恢复 C3/C4 的真实能力验收，再解决 UI 派发与执行协议。

对历史 action 14 的唯一现场原因，本材料仍没有足够 UI 请求/存档证据；除此之外，上述主要问题已有源码位置和可执行复现，不需要继续靠整条真实 API 重跑来猜。
