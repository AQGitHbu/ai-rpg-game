# AI + RPG：四类信息维护、历史摘要与生成上下文编排

- **版本**：v1.0
- **整理日期**：2026-09-09
- **用途**：固化本轮讨论的架构结论，作为后续重构与实现的依据。
- **范围**：四类长期信息的维护；完整历史与批量摘要；通过实体 ID 检索历史与实体；剧情规划、旁白、NPC 对白和玩家选项的上下文组织；生成后的校验与提交。
- **说明**：文中的数据结构是建议的逻辑结构，不要求必须拆成同名数据库表。标注为“建议参数”或“实现约束”的部分，用于补齐实现边界，不表示现有项目已经具备这些能力。

---

## 1. 最终架构概览

### 1.1 四类长期信息

| 类别 | 核心问题 | 主要内容 | 更新方式 |
| --- | --- | --- | --- |
| 第一类：实体 Entity | 世界里有什么？现在是什么样？这个角色知道什么？ | 玩家、NPC、地点、道具等；当前状态；显式关系；角色知识与记忆引用 | 创建实体、修改当前字段、更新角色认知 |
| 第二类：历史 History | 已经发生过什么？ | 已发生剧情的完整记录、结构化事件、实体关联索引、历史摘要 | 原始历史追加；摘要批量更新；索引随事件维护 |
| 第三类：剧情状态与规划 Story State | 故事目前进行到哪里？有哪些目标？接下来可如何发展？ | 当前阶段、目标、已有悬念、后续方向、篇幅进度 | 根据实际结果更新；未来计划允许调整 |
| 第四类：基础设定 Game Definition | 这是怎样的游戏与世界？ | 题材、世界观、风格、篇幅、初始角色设定、基础叙事约束 | 初始化写入；正常剧情推进一般不修改 |

**角色知道什么，放在人物 Entity 内；摘要与历史索引，属于第二类历史的派生数据。它们不另外增加长期信息类别。**

### 1.2 四个生成职责

| 生成职责 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 剧情规划器 | 规划从当前输入到下一个决策点之间的小节；提出事件、实体变更、NPC 行为意图和选项意图 | 不直接写数据库；不能把未来计划当成已经发生的事实 |
| 旁白生成器 | 在玩家可感知、允许展示的范围内，表达场景与事件 | 不自行增加隐藏真相、角色内心或新的剧情结果 |
| NPC 对白生成器 | 依据该 NPC 的身份、认知、当前处境和获准表达的内容生成对白 | 不读取其他角色的私有记忆；不自行改变世界事实 |
| 玩家选项生成器 | 将已核准的行动意图表达为与当前对白衔接的可选文本 | 不擅自增加新行动、新分支承诺或玩家尚不知道的事实 |

这四项是**逻辑职责**，不等于每一小节固定调用四次 API。例如，小节没有 NPC 对白，就不需要该项调用；多个 NPC 也不能仅为减少调用而混用私有上下文。

旁白、NPC 对白、选项可以复用同一套表达生成代码，但每次调用的身份、可见信息和输出约束分别构造。

### 1.3 两个程序模块

**上下文构造器**负责从四类信息中取数、按权限裁剪、组织各生成器的输入。

**规则校验与结算器**负责校验行动、实体引用、状态变更和剧情包，在确定内容实际生效后提交数据。

不能让剧情规划器自己决定“哪些信息已经通过权限校验”。它的下发内容同样是需要校验的提议。

```text
四类长期信息
    ↓
上下文构造器：取数、检索、权限裁剪
    ↓
剧情规划器 → 候选小节计划
    ↓
计划校验、准备本次候选状态
    ↓
分别构造旁白 / NPC 的上下文
    ↓
旁白生成、NPC 对白生成
    ↓
结合实际对白，表达已核准的玩家选项意图
    ↓
组装剧情包 → 整体校验 → 正式提交与展示
    ↓
实体更新 + 历史追加 + 剧情状态更新
```

**不采用**：embedding、向量数据库、额外的语义相关性判断模型、每次检索再调用一次 AI 判断相关性。

## 2. 第一类：实体如何保存与更新

### 2.1 实体保存“身份”和“当前状态”

第一版至少包含玩家、NPC、地点、道具。阵营等可以按已有玩法扩展，不必为本次重构强行增加。

| 实体 | 相对稳定的信息 | 当前可变化的信息 |
| --- | --- | --- |
| 玩家 | 名称、身份背景、说话风格 | 所在位置、持有物品、认知、经历引用 |
| NPC | 名称、身份、性格、背景 | 所在位置、存活状态、关系、认知、经历引用 |
| 地点 | 名称、类型、空间关系、基础描述 | 是否开放、已发现设施、当前环境状态 |
| 道具 | 名称、类型、基础属性 | 持有者、位置、是否消耗、当前可用性 |

例如，玩家把信交给老板后，道具 Entity 的 `owner_id` 修改为老板。不要为了表达“现在由老板持有”，不断追加多个互相竞争的当前持有者字段。

“玩家曾经持有这封信、后来交给老板”的过程，另写入第二类历史。

### 2.2 知识和记忆挂在人物 Entity 上

人物 Entity 可以包含：

```json
{
  "id": "npc_innkeeper_001",
  "type": "npc",
  "name": "酒馆老板",
  "profile": {
    "identity": "经营本镇酒馆的老板",
    "personality": ["谨慎", "说话简短"]
  },
  "state": {
    "location_id": "loc_inn_001",
    "alive": true
  },
  "knowledge": [
    {
      "knowledge_id": "knowledge_021",
      "content": "破庙后殿有一口旧井。",
      "related_entity_ids": ["loc_temple_001"],
      "source_type": "initial_background",
      "source_history_id": null,
      "certainty": "believed",
      "disclosure_rule": "may_tell_player"
    }
  ],
  "memory_history_ids": ["history_042"]
}
```

字段名可调整，但要保留以下区分：

- **世界实际是什么**：由对应实体状态或已确认事件记录。
- **角色相信什么**：由该角色的知识字段记录，可能不完整，也可能错误。
- **角色向别人说了什么**：由历史中的交流事件记录，不自动成为客观真相。

`memory_history_ids` 是经历引用，不是把整段历史不断复制进每个 NPC。长期累积较多时，可以用关联表实现，逻辑上仍属于角色的记忆。

### 2.3 知识更新需要来源

角色可以因亲眼见到、参与事件、听到对话、收到信件或初始背景而获得知识。

**玩家去过破庙，不等于酒馆老板知道玩家去过破庙。**

“老板知道破庙有旧井”和“老板知道玩家昨晚住在破庙”也不是同一条知识。后者需要玩家告知、老板目击或其他明确来源。

NPC 说“我不知道”，不应直接把其知识字段改为“不知道”。这句话可能是推托或谎言，应记录为他说过的话。

### 2.4 避免重复的权威状态

同一项当前事实应有一个主要存储位置。例如，道具持有者以道具 Entity 为准，历史中的“曾由谁持有”不能覆盖它。

任务系统同理：第一版可以将目标和进度统一放第三类。如果现有系统已有任务 Entity，则任务自身状态以任务 Entity 为准，第三类通过 ID 引用，不再维护一份含义相同、可独立修改的状态。

## 3. 第二类：完整历史如何保存

### 3.1 原始历史始终保留，摘要不是替代品

第二类包含三个层次：

```text
完整历史记录：保留已发生内容，是追溯依据
历史摘要：为上下文提供较短的历史概览
事件—实体索引：支持按 Entity ID 找回原始历史
```

即使第 1～10 条历史已经被摘要，原始记录仍然保存在数据库中，后续可以再次检索。

“原文退出当前 Prompt”不等于“原文被删除”。

### 3.2 明确“一条历史”的计数单位

**建议本项目统一：一条历史 = 一个已结算的小节或交互段记录。**

一条内部可以包含多个事件、几句对白和旁白。不要有时按一句对白计数，有时按一个剧情包计数，否则“50 条”的含义不稳定。

历史记录建议保留：

```json
{
  "id": "history_042",
  "game_id": "game_001",
  "sequence": 42,
  "segment_id": "segment_042",
  "source_action_id": "action_031",
  "original_text": "玩家询问昨晚见到的记号。酒馆老板说：‘破庙后殿有口旧井，你可以去那里看看。’",
  "entity_ids": [
    "player_001",
    "npc_innkeeper_001",
    "loc_inn_001",
    "loc_temple_001"
  ],
  "events": [
    {
      "type": "information_told",
      "actor_id": "npc_innkeeper_001",
      "recipient_ids": ["player_001"],
      "location_id": "loc_inn_001",
      "related_entity_ids": ["loc_temple_001"],
      "content": "老板向玩家提供了破庙后殿旧井的线索。"
    }
  ],
  "committed_state_version": 42
}
```

`sequence` 用于同一存档内排序。实体关联既包括实际出场者，也包括对白或事件明确提到的对象。

原文用于保留表达细节；结构化事件用于记录谁做了什么、涉及哪些对象，以及支持更新和检索。不能仅靠一大段小说文本反推所有状态。

### 3.3 只记录实际发生的内容

可以进入正式历史：已发生的移动、交付、相遇、对白、观察，以及已经结算的战斗结果。

不能写成已发生事实：未选择的选项、未来大纲、预生成的候选分支、尚未结算的战斗结果。

界面上展示过哪些选项可以作为展示记录保存，但“出现一个交付选项”不等于“玩家交付了物品”。

### 3.4 历史追加，当前状态修改

例如，玩家从破庙移动到酒馆：

```text
第一类 Entity：player.location_id 修改为酒馆
第二类 History：追加“玩家从破庙抵达酒馆”
第三类 Story State：按实际结果调整当前目标或阶段
第四类基础设定：不变
```

历史事件本身不需要统一设置“活跃 / 关闭”。它描述的是已经发生的事情。

任务是否完成、线索是否解决，属于相应任务或剧情状态；只有明确的完成条件成立才更新。不能因为玩家离开地点，或摘要没有再提某件事，就把它判断为“已关闭”。

## 4. 第三类与第四类如何维护

### 4.1 第三类：当前剧情状态与后续规划

建议保留以下结构：

```json
{
  "phase": "追查失踪者",
  "current_objective": {
    "description": "向酒馆老板打听昨晚的异常",
    "related_entity_ids": ["npc_innkeeper_001", "loc_inn_001"]
  },
  "established_progress": ["玩家已经离开破庙并抵达酒馆"],
  "open_questions": ["昨夜陌生人为何出现在破庙"],
  "future_directions": [
    {
      "description": "根据打听结果，考虑返回旧地点调查或追查其他人",
      "status": "tentative"
    }
  ],
  "length_progress": {
    "target_length": "short",
    "completed_segments": 42
  }
}
```

**已经确认的进展与未来可能的方向必须分开。**

“可以考虑回破庙”不是“玩家一定回破庙”；玩家拒绝这条路，后续规划就应调整，而不是强行完成预设剧情。

它应是一份当前有效的剧情控制文档，不是另一个无限增长的完整历史副本。

### 4.2 第四类：基础设定

保存题材、世界观、叙事基调、篇幅、玩家初始身份与风格，以及稳定约束。

第一版原则：由初始化确定，普通小节生成不能自行改写。需要变更时应走明确的版本变更，而不是模型为了让某段剧情成立就改变世界规则。

玩家当前所在地、当前物品等变化信息不应反复写回初始设定，应放第一类。

### 4.3 给剧情规划器的范围

本轮采用：

**第三类当前有效剧情状态与规划，全量提供；第四类核心基础设定，全量提供。**

这里的“全量”指上述两份受控文档，不是历史上每一版计划，也不是未来无限扩充的所有背景资料。世界具体人物、地点与局部经历仍归第一、二类，按需检索。

基础设定稳定，不代表后续调用可以默认模型记得它。每次生成仍需通过当前请求或所用 API 的明确上下文机制，使这些设定实际可用。

## 5. 摘要策略：按批次滚动，不逐条重算

### 5.1 两个独立参数

| 参数 | 本轮采用值 | 含义 |
| --- | --- | --- |
| `raw_threshold` | 50 | 未被摘要覆盖的原始历史达到多少条时触发摘要 |
| `summary_batch_size` | 10 | 每次从未摘要历史的最前面取多少条合入摘要 |

注意，触发条件是**未摘要原文缓冲达到 50 条**，不是“总历史超过 50 后，每次都摘要”。

### 5.2 实际变化示例

以下假设每次摘要都已成功完成：

| 已提交历史总数 | 摘要覆盖 | Prompt 中保留的连续近期原文 | 本次摘要动作 |
| --- | --- | --- | --- |
| 40 | 无 | 第 1～40 条 | 不触发 |
| 49 | 无 | 第 1～49 条 | 不触发 |
| 50 | 第 1～10 条 | 第 11～50 条，共 40 条 | 首次摘要第 1～10 条 |
| 51 | 第 1～10 条 | 第 11～51 条，共 41 条 | 不触发 |
| 59 | 第 1～10 条 | 第 11～59 条，共 49 条 | 不触发 |
| 60 | 第 1～20 条 | 第 21～60 条，共 40 条 | 旧摘要 + 第 11～20 条，生成新摘要 |
| 70 | 第 1～30 条 | 第 31～70 条，共 40 条 | 旧摘要 + 第 21～30 条，生成新摘要 |

因此，正常稳态保留的不是固定“最近 50 条原文”，而是**摘要 + 最近尚未被摘要覆盖的 40～49 条原文**；达到 50 条时进行下一批压缩。

每新增约 10 条已提交历史，才需要一次摘要调用，而不是每条历史都附加一次调用。

### 5.3 每次摘要的输入与输出

输入：

```text
上一版有效摘要
+ 本次最早的 10 条未摘要历史
+ 这些内容已携带的实体 ID 引用
+ 摘要长度和忠实性约束
```

输出建议：

```json
{
  "version": 2,
  "covered_through_sequence": 20,
  "text": "玩家曾在破庙借宿，遇到一名陌生人，随后按照其建议到酒馆打听消息。",
  "entity_refs": ["player_001", "loc_temple_001", "npc_stranger_001", "loc_inn_001"],
  "source_batch": {
    "from_sequence": 11,
    "to_sequence": 20
  }
}
```

`covered_through_sequence = 20` 表示摘要概览覆盖第 1～20 条；并不表示每一条的全部细节都仍在摘要中。

摘要应尽量保留重要经历、关键因果、主要人物与地点、已经确定的结果。不能增加未发生事件，不能把角色传言总结成客观真相，也不能自行判定任务已经完成。

### 5.4 摘要的实体引用如何维护

原始历史已经带有实体 ID。摘要生成时，只允许使用旧摘要与本批原文提供的合法 ID，并由程序校验引用。

摘要 `entity_refs` 应对应本版摘要实际保留的对象，不应无条件把全游戏所有历史实体 ID 都累计塞入每次 Prompt，否则实体上下文仍会无限膨胀。

完整的事件—实体索引始终保留在数据库。某实体没有出现在新摘要中，不代表它或它的旧事件被删除。

### 5.5 摘要失败或延迟时不能出现历史断档

摘要维护两个关键值：

```text
latest_committed_sequence：最新已提交历史序号
covered_through_sequence：当前有效摘要覆盖到的历史序号
```

尚无有效摘要时，`covered_through_sequence` 视为 0。构造近期原文时，读取：

```text
covered_through_sequence + 1
到
latest_committed_sequence
```

例如，新摘要失败，旧摘要仍只覆盖第 1～10 条，但历史已到第 61 条，则暂时读取第 11～61 条。不能机械截成最近 50 条，从而让第 11 条既不在摘要、也不在原文中。

只有新摘要成功并通过校验后，才原子替换摘要内容及覆盖序号。失败时保留旧版本，不删除原始历史。

摘要可以放在主提交后的维护队列中执行，不要求成为每次剧情生成的串行步骤；但同一存档的摘要更新应避免并发覆盖。若未摘要缓冲增长到超过上下文预算，应先补做摘要或阻塞该次构造，不能静默漏掉一段历史。

### 5.6 条数阈值之外仍需长度预算

50 条只是本轮采用的业务阈值。如果单条剧情特别长，同样的条数也可能产生过大的输入。

**实现约束**：摘要长度、原文输入和最终 Prompt 都需要可配置的长度预算。超预算时可提前按批压缩；本文不另行固定具体 token 数。

## 6. Entity ID 如何进入事件、摘要与生成结果

### 6.1 正式 ID 由程序分配

新实体通过规则校验后，由程序分配正式 ID。之后每次向 AI 提供该实体时，同时提供 ID、名称与必要属性。

```text
loc_temple_001：破庙
npc_innkeeper_001：酒馆老板
```

模型在结构化输出中引用已有 ID；程序检查它是否存在、类型是否正确，以及是否属于本次允许引用的范围。

### 6.2 初始化中的新实体使用临时引用

初始化时，AI 可能需要在同一候选计划里提出新地点、新人物，并安排它们参与事件。

建议允许请求内临时引用，例如 `new_location_1`。程序批准创建后分配正式 ID，并统一替换该候选计划中的临时引用，再进入下游生成。

**临时引用不是 AI 创建正式 ID 的权限。** 未批准的候选实体不能写进正式历史。

### 6.3 事件引用尽量由动作直接产生

例如移动动作已经包含：

```text
actor_id = player_001
from_location_id = loc_temple_001
to_location_id = loc_inn_001
```

这些 ID 可以由程序直接附在历史记录上，不需要再次调用 AI 识别。

对于对白中提到、但不在当前场景的实体，由结构化生成结果声明引用，程序验证后附加。

### 6.4 检索以 ID 为主，不依赖重新猜关键词

讨论中所说的“原文与摘要命中实体”，在实现上优先表示：

**读取原文事件和摘要附带的 `entity_ids / entity_refs`，而不是每次重新从文本猜实体名称。**

名称和别名匹配可以作为旧数据或自由输入的辅助入口，但不能替代 ID 体系，尤其要避免同名角色、简称和改名造成误匹配。

## 7. 如何从摘要与原文抽取实体，再补充旧历史

### 7.1 基本流程

```text
当前行动、场景、交互对象
+ 全量当前剧情状态
+ 历史摘要
+ 尚未摘要的近期原文
    ↓
提取其中已有的 Entity ID 引用
    ↓
读取这些实体的当前数据
    ↓
按 Entity ID 查询完整历史中的相关旧记录
    ↓
去重、按新近程度排序、限量
    ↓
形成剧情规划器上下文
```

这里不要求在第一次生成破庙时，就预先规定玩家以后必须回来。只要近期历史或摘要中仍有破庙引用，规划器就有机会重新利用这个已有地点。

### 7.2 第一轮实体集合

实体 ID 来源包括：

| 来源 | 作用 |
| --- | --- |
| 当前玩家、地点、交互 NPC、行动涉及的道具 | 保证眼前动作可以被正确理解 |
| 近期原文的 `entity_ids` | 保留最近经历过或提到的人物、地点 |
| 摘要的 `entity_refs` | 保留更早历史中仍被摘要保留的对象 |
| 当前剧情目标中的显式实体引用 | 保留当前任务直接依赖的对象，但不把它作为唯一召回入口 |

对这些 ID 去重后，批量读取实体的**当前状态**。

若实体很多，可先给全部候选实体的轻量卡片，再为当前参与者、目标对象和选中的关联对象补充详细字段。不要求把每个 NPC 的全部知识与全部记忆都展开。

### 7.3 实体之间的显式关联

可以维护已确认的关系，例如人物所在地点、物品持有者、地点所属区域，以及历史中明确形成的联系。

程序能从动作结果直接得出的关系，直接更新；不能从结构化数据推出的关系，可以由规划器随本次计划提议，校验后写入。

不为了检索再新增一次“关系识别 API”。关系应有明确含义，不能仅因两个人在同段文字出现，就假定他们彼此认识或互通秘密。

建议只做有数量上限的一跳扩展，不无限沿关系图展开。

### 7.4 第二轮：按实体找回已被摘要的原始历史

例如摘要只留下“玩家曾在破庙借宿”，但没有保留当晚的对话。

检索过程为：

```text
摘要包含 loc_temple_001
    ↓
读取破庙 Entity 的当前数据
    ↓
通过事件—实体索引，找出关联 loc_temple_001 的历史
    ↓
优先找近期原文中没有包含的旧记录
    ↓
选取有限条原文，补给剧情规划器
```

这批补充历史作为独立的 `recalled_history` 输入，不需要为了本轮生成再重新改写摘要。

### 7.5 不使用语义相似度，只采用轻量排序

首版规则：

1. 必须精确命中候选 Entity ID。
2. 已在近期原文中的历史不再重复加入。
3. 对其余命中历史按 `sequence` 从新到旧排序。
4. 设置每实体上限、补充历史总上限及最终长度上限。

可以把“越旧越衰减”直接落实为“越新的优先”。首版不必同时引入复杂权重公式；单纯按时间单调衰减，在其他条件相同时，排序结果也就是按新近程度排序。

**建议参数，尚非讨论中定死的数值**：每个实体最多补充 3 条旧历史，全部实体合计最多 10 条。参数应可配置，后续通过实际剧情测试调整。

实际取数可按各实体候选轮流填充并去重，避免一个高频地点占满全部名额。选出的历史在 Prompt 中按发生顺序排列，并标注为旧事件。

### 7.6 不无限递归检索

补充历史可能又提到其他实体。可以给这些新引用附一张最小实体卡，帮助理解，但首版不再由它们继续无限召回下一批历史。

```text
原文 / 摘要 → 实体 → 一轮历史补充
```

这轮补充有明确终点和预算。

### 7.7 该轻量方案的边界

如果一个很早的实体既不在近期原文中，也被摘要遗漏，且不属于当前对象或显式关系扩展，它就可能不会进入本轮上下文。

如果某条重要旧记录被更新的同实体事件挤出限额，本轮也可能看不到它。

完整保存历史解决的是“还能追溯”，不是保证“每次都自动想起一切”。本方案接受这个轻量检索边界，不引入 embedding 来承诺完全召回。

## 8. 剧情规划器最终拿到什么

推荐的逻辑输入：

```json
{
  "game_definition": {},
  "story_state": {},
  "current_action": {},
  "current_context": {
    "player_id": "player_001",
    "location_id": "loc_inn_001",
    "interacting_npc_ids": ["npc_innkeeper_001"]
  },
  "history_summary": {},
  "recent_history": [],
  "recalled_history": [],
  "entities": [],
  "generation_constraints": {
    "stop_at_next_decision_point": true,
    "new_entity_budget": 2
  },
  "base_state_version": 42
}
```

示例中的新增实体预算仅用于说明字段，不代表固定允许新增两个实体。

规划器需要明确理解：

- Entity 是当前状态；旧历史中的状态只说明当时情况，不能覆盖现在。
- 历史中的对白是某人说过的话，不一定是真相。
- Story State 中的未来方向是可调整计划，不是已发生事件。
- 新地点、新 NPC 可以提议，但优先考虑已有对象，并接受创建预算与重复检查。
- 本次输出到下一次玩家决策为止，不提前替玩家执行尚未选择的分支。

规划器可以读取当前所需的隐藏信息，但不必每次拿到全部世界实体、全部角色记忆或完整历史。

## 9. 旁白、NPC 对白和玩家选项如何取上下文

### 9.1 三者复用编排机制，但不能复用同一份全局内容

| 信息 | 旁白生成器 | NPC 对白生成器 | 玩家选项生成器 |
| --- | --- | --- | --- |
| 语言与叙事风格 | 使用旁白所需部分 | 使用该 NPC 所需部分 | 使用玩家表达所需部分 |
| 当前场景 | 玩家此刻可观察的内容 | 该 NPC 可感知的内容 | 玩家已观察到的内容 |
| 历史与记忆 | 玩家已知或可被叙述的相关事件 | 该 NPC 经历、听闻或知道的相关内容 | 玩家已经获得的相关内容 |
| 角色属性 | 必要的可见特征 | 该 NPC 身份、性格、状态 | 玩家身份、说话风格 |
| 本次计划 | 获准展示的场景与事件 | 已核准的行为、表达意图与事实引用 | 已核准的行动意图 |
| 刚完成的对白 | 需要承接时提供已发生部分 | 多人依次对话时，只提供其听到的部分 | 提供玩家实际听到的对白 |
| 全局总纲、幕后真相 | 不整包提供 | 不整包提供 | 不提供未揭示内容 |

全局历史摘要可能包含秘密，因此不能把规划器使用的摘要原封不动给另外三个生成器。

### 9.2 隔离由程序执行，而不是只靠规划器自觉

如果规划器知道幕后真相，并写下一句“让老板暗示地板下藏着密道”，即使下游没有收到完整总纲，秘密仍可能通过这句指令传过去。

因此必须对规划器的下游任务做校验：

```text
规划器提出某 NPC 要表达的信息
    ↓
检查 NPC 是否拥有该知识或允许形成该判断
    ↓
检查当前小节是否允许向玩家披露
    ↓
生成经过裁剪的表达任务
```

优先让计划引用已存在的知识条目、实体字段或事件，而不是任意写一段未经检查的“语义指令”直接传给下游。

“剧情规划器建议披露”不是授权本身。不能为了让这句话合法，就倒过来自动给 NPC 增加此前没有来源的知识。

### 9.3 NPC“不知道”与“知道但不说”不同

NPC 的真实认知保存在 Entity 中；这次对白需要哪些认知，再按任务裁剪。

例如老板知道秘密但不愿透露：

```text
身份：酒馆老板
当前意图：回避玩家对昨晚来客的追问
本次可表达内容：承认昨晚营业；不提供来客去向
表达限制：不得新增地点、人物身份或具体线索
语气：谨慎、简短
```

若完成这段对白不需要秘密的具体内容，就不把秘密正文传入该次表达调用。但数据库里的老板仍然“知道秘密”，不会被改写成真正不知情。

确实需要角色依据秘密进行判断的情形，要明确其可用知识与本次披露范围。上下文裁剪不能代替这一认知区别。

### 9.4 选项先定行动意图，后定表达

剧情规划器先提出并经规则校验的意图，例如：

```text
选项 A：追问昨夜陌生人的去向
选项 B：结束交谈，返回破庙调查
```

NPC 对白完成后，玩家选项生成器再参考实际措辞，生成自然衔接的选项文本。

```text
A：“那人离开时，有没有说要去哪儿？”
B：“我回破庙看看，兴许还能找到线索。”
```

每个选项文本绑定稳定的行动 ID 和参数。表达生成器不能把“回破庙调查”改成“打开井底密室”，因为后者额外假定了玩家知道密室并且能够打开。

若最终对白没有提供某个选项所必需的信息，应修正对白或上游意图，不能由选项生成器自行补出玩家不知道的知识。

自由输入仍然经过“意图解析 → 合法性判断 → 行动结算”，不会因输入一句话就直接改变世界。

### 9.5 表达生成仍需检查，不能声称绝对无泄漏

结构化字段和 ID 校验可以检查引用与状态约束，但不能单独证明自由文本完全没有暗示、编造或越界。

首版应收紧表达任务：限定事实来源、限定可新增内容、保留稳定行动参数，对失败块定点重新生成或采用受控文本回退。不为每句话额外引入一个相关性或判定模型，也不把“只给部分上下文”描述为百分之百保证。

## 10. 生成后何时写回四类信息

### 10.1 正常流程：先生成与校验，再正式提交

```text
读取已提交状态版本 V
    ↓
构造规划器上下文
    ↓
生成候选计划：事件、实体提议、行为与选项意图
    ↓
校验计划，形成只在本次请求内有效的候选状态
    ↓
从候选状态构造各自有权限的表现上下文
    ↓
生成旁白、NPC 对白、玩家选项
    ↓
组装并校验完整剧情包
    ↓
确认本小节获准实际发生，且基础状态版本仍有效
    ↓
原子提交：实体修改 + 历史追加 + 剧情状态更新
    ↓
展示已提交的小节，停在下一个决策点
```

下游生成需要看到本小节已经规划但尚未正式提交的状态，例如“玩家已到酒馆”。应读取本次请求的候选状态，而不是提前污染正式数据库。

### 10.2 一次提交分别更新什么

| 信息 | 提交内容 |
| --- | --- |
| 第一类 Entity | 批准的新实体、当前状态变化、角色实际获得的知识、关系变化 |
| 第二类 History | 已发生小节原文、结构化事件、实体关联索引 |
| 第三类 Story State | 本次实际进展、当前目标变化、修订后的后续方向 |
| 第四类 Game Definition | 通常不变；普通小节提交无权自行修改 |

这些正式状态变化应作为同一次原子提交。不要出现“物品已经交出，但历史没有记录”“历史说 NPC 已死亡，但 Entity 仍存活”等半完成状态。

摘要是历史的派生维护，不要求与上述主事务一起完成。

### 10.3 预生成不等于实际发生

“剧情包生成完成、校验通过”只是可提交条件之一。

若它是玩家尚未选择的预生成分支，就仍然只是候选包，不能更新实体、玩家认知、剧情进度或正式历史。只有对应行动真正被选中，并确认候选包所依据的状态仍有效后，才允许提交。

若小节中途存在尚未决定的玩家操作或尚未结算的战斗，应在那个边界暂停。不能把后面的胜利、奖励和对白提前提交。

### 10.4 重试与版本检查

建议给行动或小节分配唯一提交键，并记录 `base_state_version`。

同一请求重试不能重复获得道具、追加相同历史或重复推进阶段。若生成期间世界状态已变化，应重新校验或重新生成，不能直接把旧结果覆盖最新状态。

剧情包本身是运行时产物，可以缓存，也可为回放或排错存档，但它不是第五类权威世界状态。

## 11. 完整例子：破庙 → 酒馆 → 可能返回破庙

### 11.1 已发生的内容

玩家曾在破庙借宿，与陌生人交谈，对方建议去酒馆打听。玩家随后抵达酒馆。

系统已保存：

```text
Entity：破庙、陌生人、酒馆、老板、玩家
玩家当前位置：酒馆
History：破庙借宿、与陌生人交谈、前往酒馆
Story State：当前目标是向老板打听
摘要：可能只保留“玩家在破庙借宿后，前往酒馆打听”
```

这里没有预设“玩家必须再次返回破庙”。

### 11.2 构造规划器上下文

摘要携带 `loc_temple_001`，近期原文也可能仍然引用破庙。

系统因此读取破庙 Entity，再按其 ID 查询完整历史，找回有关借宿和陌生人对话的有限条原文。

此时规划器知道：破庙已经存在、玩家去过那里、曾发生什么，以及当前在酒馆的原因，不必凭空创造一个替代地点。

### 11.3 规划下一小节

假设老板 Entity 的初始知识或已有经历中，明确记录了“破庙后殿有旧井”，且当前允许告诉玩家。

规划器可以提出：老板提供旧井线索；玩家可选择追问陌生人或回破庙调查。

如果老板没有这条知识的来源，就不能仅因规划器想让玩家回破庙，直接让老板说出该秘密。需要改用合法的信息来源，或换一种剧情安排。

### 11.4 表达与玩家选择

NPC 对白生成器只得到老板身份、其相关知识、本次可以透露的线索和当前对话，不得到全局幕后解释。

玩家选项生成器得到玩家已经听到的对白，以及两个已核准的行动意图，生成可选文本。

这一小节提交时，记录的是“老板提供线索，玩家听到了该说法”。玩家的位置仍在酒馆。

只有玩家下一步真正选择并完成返回破庙，才更新位置并追加新的移动历史。玩家选择其他道路，则据此调整后续规划。

## 12. 最小维护规则与验收清单

### 12.1 最小维护规则

| 时机 | 程序执行的维护 |
| --- | --- |
| 初始化成功提交 | 创建初始实体、写入初始知识、保存基础设定与剧情状态、追加已发生的开场历史 |
| 每个小节成功提交 | 更新实体与认知；追加完整历史；同步维护实体关联索引；更新剧情状态 |
| 未摘要历史达到 50 条 | 取最早 10 条与旧摘要合并，成功后推进摘要覆盖序号 |
| 构造规划器上下文 | 摘要 + 未摘要原文 → 实体 ID → 当前实体 → 限量旧历史补充 |
| 构造表现层上下文 | 按旁白视角、NPC 认知或玩家认知再次裁剪，不直接复用全局包 |
| 生成失败或校验失败 | 不提交正式世界变化；修复或重新生成失败部分 |
| 请求重试或预生成包使用 | 检查唯一提交键与状态版本，防止重复提交和过期结果生效 |

### 12.2 最小索引建议

建议具备：同一存档内按历史序号查询的索引、Entity ID 到历史记录的关联索引、实体 ID 唯一索引，以及行动/小节提交键唯一约束。

这些都是结构化数据查询，不需要向量检索系统。

### 12.3 验收清单

- [ ] 历史达到 50 条时，摘要覆盖第 1～10 条，原文保留第 11～50 条；第 51 条不会再次触发摘要。
- [ ] 历史达到 60 条时，旧摘要与第 11～20 条合并，摘要覆盖到第 20 条；旧原文没有被删除。
- [ ] 摘要失败时覆盖序号不推进；下一次上下文不会遗漏未摘要历史。
- [ ] 摘要提到破庙时，能通过正式 ID 读取破庙当前状态，并检索被压缩掉的原始经历。
- [ ] 补充历史有每实体上限、总量上限、去重与长度限制，不发生无限递归。
- [ ] 玩家去了某地，不会自动给未目击的 NPC 增加该知识。
- [ ] NPC 撒谎不会把其真实认知改成谎言内容，也不会直接改变客观世界事实。
- [ ] 规划器的隐藏信息不会因为被写进下游指令，就绕过信息权限检查。
- [ ] 玩家选项不泄露尚未得知的信息，且文本始终绑定核准的行动 ID 与参数。
- [ ] 未选择的预生成分支不写入正式历史，不提前发放物品、不更新位置、不推进剧情。
- [ ] 同一提交重试不会重复写入；旧历史不会覆盖实体当前状态。

---

## 13. 最终结论

本轮采用的整体方案是：

**四类长期信息作为权威来源；完整历史始终保留；按“未摘要原文达到 50 条，每次合并最早 10 条”的方式滚动摘要；从摘要与近期原文携带的 Entity ID 获取相关实体，再按 ID 从完整历史中限量找回旧记录。**

剧情规划器获得完整的当前剧情控制信息与核心基础设定，以及按上述方式提取的实体和历史。旁白、NPC 对白、玩家选项则分别按自己的视角、知识与披露范围构造上下文。

生成结果先作为候选计划和候选剧情包，经过校验，并且在对应内容实际获准发生时，才统一提交实体变化、历史记录和剧情进展。

**摘要负责概览，原文负责追溯，Entity 负责当前状态与角色认知，剧情状态负责推进方向，程序负责权限与结算；AI 负责在这些边界内规划和表达。**
