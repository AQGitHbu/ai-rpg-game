# 分阶段剧情规划、旁白、角色表现与玩家对白选项设计

## 1. 状态、目标与范围

本文是待实施 Spec，不描述已实现能力，不包含执行 Plan。本文的维护不修改代码、当前阶段指针或现行系统契约。

将现有一次生成世界变化、场景、NPC 台词和玩家选项的生产链，改为四类独立生成职责：剧情规划、旁白、单个 NPC 角色表现、玩家选项表达。各类生成使用独立请求与服务端裁剪的上下文；一个旁白单元、一个 NPC 表现单元和一处普通决策的包，正常成功路径为四次调用，按依赖关系执行，不要求全部串行。对外仍发布一个完整、已批准的叙事包。

产品目标：

- NPC 只在自己的认知和披露权限内说话，不因参与剧情生成而获知未来或其他角色秘密。
- 旁白采用玩家视角，只呈现当前可感知的内容，不以全知叙述泄露隐藏动机、幕后真相或未来安排。
- 玩家对白选项只包含玩家直接说出的话，不含动作、心理、语气或小说式引导说明。
- 两个普通决策选项代表实质不同的策略，并产生可追踪的后续剧情分化。
- 生成内容经过规则审批；规则拥有事实、行动合法性、战斗、关系、知识、任务与结局裁决权。
- 保留连续内容预生成、显式失败重试与原子发布，避免阶段间部分成功暴露给玩家。

本设计覆盖初始化和后续 NPC 决策、相关世界变化、旁白、未来连续步骤、选项与失败恢复。不新增任意自由行动解析器、自动角色聊天或独立 misinformation 生命周期，不改变短篇/中篇预算及战斗裁决规则。

## 3. 调用与审批链

1. 读取已提交的规则状态与本次生成任务，固定输入 revision 和生成身份。
2. 剧情规划器提出结构化骨架。
3. 服务端审批骨架、世界变化、步骤和两条分支语义，构造有条件的预览状态。
4. 服务端构建表达单元的依赖图，分别投影指定步骤时点的玩家感知范围，以及单个 NPC 的知识与表演任务。
5. 旁白生成器与角色表现器使用各自的独立请求生成内容；服务端分别审批。有依赖的单元等待上游通过，再按事件顺序投影输入。
6. 服务端投影玩家在该决策时点可知的信息、将在选项前展示的获批旁白和对白，以及两条安全选项语义。
7. 玩家选项表达器生成两个对白 label；服务端审批。
8. 整包进行跨阶段一致性检查并原子发布为 ready。

基础调用数为一次规划，加旁白生成单元数、角色表现生成单元数和选项表达单元数；不含重试与可选的额外模型审核。一个旁白单元、一个 NPC 表现单元、一处普通决策且无失败时为四次调用。同一个 NPC 在不同依赖时点的表演也可能需要多个单元；没有旁白或决策内容时，跳过相应单元，不为凑调用数生成内容。生成单元具有稳定身份，关联职责、step、speaker（如适用）、顺序和依赖版本。阶段完成不新增玩家回合，四类生成职责不改变现有三类业务触发边界。

独立角色只有在输入互不依赖时才可并行。乙需要听到甲的台词才能回答时，乙必须等待甲审批通过，并只接收其实际听到的内容。禁止把多个角色的私密上下文拼接到同一次角色请求。

旁白与角色表现固定分开请求，不设置“上下文安全时合并”的例外，也不与规划器合并。独立环境旁白和 NPC 台词可以并行；旁白若描述获批表演动作或对白之后的反应，必须等待对应角色单元审批通过。NPC 若回应先前环境事件，只接收自己可观察到的结构化事件；需要引用具体措辞时，再接收经过权限过滤的已批准文本。依赖图必须无环，不能让同一对生成单元互相等待；连续互动按事件顺序拆分为多个单元。

## 4. 第一阶段：剧情规划

### 4.1 权限与职责

规划器可获得与当前任务相关的世界真相、剧情需求、角色目标、规则结果和因果记忆。“上帝视角”表示拥有规划所需信息，不表示可以读取全部原始账本、所有历史玩家原文或任意系统数据。

规划器输出结构化提案，不输出最终旁白、NPC 台词或玩家 label，不直接执行动作。它可以提出新增内容和路线，但不能任意 patch 状态、设置关系数值、宣告战斗胜利或自动完成玩家尚未执行的行动。

规划器可提出“村长放下茶杯”这样的结构化场景动作，并分别标注发生条件、观察者和表达用途；隐藏的“村长正在试探玩家”属于规划依据，不能随动作提案进入旁白请求。结构化提案中的描述不是最终展示文案，不得未经表达生成与审批直接投影给玩家。

### 4.2 骨架最低字段

以下为待实现的逻辑契约，具体类型名称不限定：

| 数据 | 必需语义 |
| --- | --- |
| 身份与依赖 | job、骨架版本、输入 revision、规则版本、依赖摘要，由服务端提供或铸造 |
| 世界变化提案 | 新实体与事实、引用、创建依据、可见性、知识来源；区分背景事实与未来事件 |
| 步骤 | 局部 stepKey、先后依赖、触发条件、地点、参与者、需表现的事件、后继步骤 |
| 认知变化 | 哪个已成立事件使哪些 audience 观察或获知什么；不得无来源全员同步 |
| 表演任务 | speaker、受众、当前交流目的、必须回应的节拍、允许透露的信息引用 |
| 旁白任务 | 玩家视点、步骤内时点、可感知事件与动作引用、需要呈现的节拍、对角色表现等上游单元的依赖；隐藏动机与规划理由不进入表达输入 |
| 决策 | 恰好两条普通选项的意图、主题、目标、行动候选及分支契约 |
| 终点 | 下一处玩家决策或受规则约束的终幕；禁止跨未选择的分支继续确定未来 |

步骤图无环、引用唯一且闭合，沿用最多 12 个连续步骤的上限。移动、交付、开战必须有实际玩家动作触发，不能因对话表达了意愿就自动执行。

审批必须验证类型、实体引用、空间可达性、参与者在场、预算、主线可完成性、事件前提、知识来源和分支可执行性。规划中的新规则能力不在支持集合内时，返回明确拒绝，不能保留一个永远无法执行的候选。

## 5. 选项分化与规则执行

### 5.1 分化标准

两条普通选项必须表达明显不同的行动策略，例如合作与拒绝、公开求证与私下交易、保护一方与支持另一方。不同用词、同义询问或仅语气强弱不算分化。

每条选项的内部契约必须绑定稳定 candidateId、受支持的 Action/DialogueAct、结构化主题，以及可由规则消费的分支标识和条件结果。AI 只提议，服务端解析、批准和铸造正式 token。隐藏后果不进入选项表达请求或客户端。

两条选项至少在一项有玩法意义的状态或后续可用内容上分化：任务目标/路线、合作或访问条件、资源与承诺、事实获取渠道、冲突处理方式或结局资格。单独的 trust 数值不同不足以通过，除非它在明确的后续条件中改变可用内容。

差异必须在本次规则结果或下一处正式决策前可观察到。可以在之后汇合，但必须保留已产生的状态差异与因果证据，不能下一轮只换句台词便抹平。

### 5.2 不以文本伪造分支

既有规则若只能处理 dialogueAct 导致的关系变化，实施必须补齐有界、类型化的分支承接能力，才能宣称满足本 Spec。不能只往 prompt 增加“分支要不同”，也不能由下一次 AI 自由猜测上一选项意味着哪条路线。

branch contract 只能声明受支持的条件与效果类型，不允许自由脚本或任意字段路径。每条分支需有可完成性验证，拒绝合作仍应有合理后果和可继续路径；不承诺每个分支都获利。

玩家点击 token 后，规则验证当前 revision、候选身份、前提与资源，提交实际选择和结果；下一次规划读取该结果。未选择的分支保持提案性质，不写入已发生事件、玩家知识或任务完成状态。

### 5.3 自定义输入

保留当前焦点 NPC 自定义输入入口，本轮文本按已有中性 talk/ask 通道承接。文本是意图而非事实，不能凭“我已经交钱”“我杀了敌人”触发资源或战斗结果。

规划器可据原文提出下一步策略与合法选择，但不得事后篡改已经提交的规则裁决。若用户提出不属于两个固定选项的第三种方案，可以回应并在下一决策提供可执行候选；本 Spec 不承诺任意原文自动转成新规则动作。

## 6. 角色表现与认知隔离

### 6.1 独立投影

每次角色请求只包含一个 speaker 的人格、当前目标与情绪、关系的必要投影、有来源的知识及其确定程度、允许披露的信息、可观察现场、实际听到的当前话语、有限相关互动和当前表演任务。

不传完整骨架、隐藏分支后果、未来真相、其他 NPC 私密知识、完整世界状态或隐藏结局条件。摘要、实体描述、任务标题、记忆、引用名称和修复提示同样执行过滤。自由文本、AI 提案和被拒绝输出均视为数据，不能变成权限指令。

服务端投影决定权限，规划器不能通过“请暗示凶手身份”等任务描述扩大 speaker 权限。角色任务必须与可说事实交叉校验。

### 6.2 知道与可以说

知道某事不意味着可以披露。knowledge 的 certainty、disclosure 与 audience 分别保留。疑似事实只能用不确定表达，NPC 的说法不自动成为世界真相。

为最小化泄露，本设计不向角色生成请求提供禁止披露的秘密正文；必要时只提供经过批准的行为约束，例如“拒绝解释委托来源”。这会限制依赖秘密细节的细腻表演，但不能用表演需要作为传递完整秘密的理由。

### 6.3 输出与校验

输出包含 speaker/step 引用、直接台词、情绪和不改变权威状态的表演动作，以及句段级事实/事件引用。递交物品、伤害、知识传播和承诺成立等具有规则后果的行为必须匹配骨架与实际触发，不能由舞台动作凭空完成。

表演动作是供服务端审批与旁白投影的结构化候选，至少绑定 actor、step、顺序、动作类型、涉及对象与可观察范围；其说明文本不是最终旁白，不直接展示。无状态后果的停顿、视线和姿态可由角色表现器提出；新增对象、可调查痕迹、具有证据意义的行为或改变行动条件的动作必须回到规划审批。已获批的情绪表达也不自动写入 NPC 动态情绪组件，持久状态变化仍需规则依据。

角色表现器不生成旁白。获批表演动作如需由旁白呈现，服务端只向下游旁白单元投影玩家能感知的部分，并保留动作与来源引用；旁白不能重写成另一个动作或重复执行其规则后果。

校验身份、在场性、时点、事实引用、certainty/disclosure、任务回应和禁止泄露。仅检查模型自报引用不够：必须加入正文与许可事实的语义一致性检查及隐藏信息泄露测试。无法确定安全的内容拒绝或进入明确审核失败，不靠关键词替换拼成成功对白。

确定性规则无法完全证明任意自然语言无语义泄漏。本设计的主要保障是输入最小化、结构化引用和跨视角测试；如引入额外模型审核，须单列请求、预算与失败语义，不能隐含在基础调用数的口径中。

实施前必须明确正文审核中哪些判据由确定性检查覆盖、哪些仅由离线真实文本验收评估、哪些需要额外在线审核，并为实际在线检查定义通过、拒绝和不可判定结果。不能用空实现或仅校验引用宣称完成语义审核，也不能要求确定性校验器证明全部自然语言安全。若配置在线审核，其拒绝或不可判定均阻止发布，并受同一任务预算约束；在线审核仍不构成绝对无泄漏保证。

## 7. 旁白与未来步骤

### 7.1 独立的玩家视角投影

旁白生成器只接收玩家在该地点、该时点能感知的现场、获批事件与动作、必要的玩家已知信息、叙事风格及当前旁白任务。不接收完整骨架、幕后真相、NPC 私密知识与内心目标、隐藏分支后果或未来安排。任务描述、实体名称、摘要、记忆和修复提示同样裁剪，不能只给完整上下文加“玩家可见”标签。

旁白始终使用独立请求，规划器和角色表现器均不附带生成最终旁白。玩家可感知内容也不自动成为 NPC 可知内容；两种投影分别根据观察位置、在场性、受众和事件顺序建立，不共享一个通用场景上下文。

### 7.2 输出与审批

输出包含 step、步骤内顺序、旁白节拍、正文和句段级事实/事件/动作引用，不输出 NPC 直接台词、玩家选项、Action 或 effect。审批检查玩家视角、时点、来源、必需节拍、与获批表演的一致性和正文语义；不能仅凭合法引用认定正文无泄漏。

旁白可描述可观察的迟疑、停顿或动作，不能把隐藏动机写成确定事实。例如，“村长放下茶杯”可以在对应动作获批且玩家可见时呈现；“村长故作镇定，试探你掌握了多少证据”不能因规划器知道其动机而成为旁白。示例只说明权限边界，不作为生产模板。

旁白不能自行新增线索、知识传播、物品转移、伤害或其他权威后果；有玩法意义的新增内容必须回到规划审批，并使依赖旧产物的下游失效。旁白与对白按获批场景顺序装配，不能因并行请求先完成就提前展示或改变因果顺序。

### 7.3 未来步骤与条件消费

未来连续步骤可以预生成，但使用“在该步骤条件成立时”的认知快照。未来抵达 NPC 不得获得此前不在场的私聊；必须通过真实见证或显式传播事件获得信息。

胜利后对白只能挂在胜利条件下；战败、撤退或实际执行与预期不符时不能消费。尚未发生的知识变化只能进入条件预览，不提前污染 NPC knowledge 或记忆。到达步骤时再次验证依赖与前提；失效内容不可展示，返回稳定错误，不由移动/战斗临时启动另一条 AI 链。

生成发布时的 revision CAS 与未来步骤消费时的有效性是两种检查。已发布 bundle 允许经过其预期的规则回合推进，不能仅因 revision 增加就整体失效。每个未来步骤记录实际依赖的实体状态、知识来源、前置事件与条件；消费时按真实状态复核这些依赖，并按当前 revision 铸造或验证 token。无法在预生成时确定的战斗剩余血量、资源损失或临场反应不得写死在未来台词里；内容只能依赖对应条件能保证的结果。

不得预生成依赖下一次未消费选择的确定剧情。确定不受新选择影响的内容在后台尽早准备，保留阅读顺序和交接交互。

## 8. 玩家选项表达

### 8.1 输入与输出

输入只含玩家截至当前决策可观察或已获知的信息、将在选项前展示的已批准旁白与 NPC 当前对白、必要的公开现场信息，以及两个批准候选的安全意图说明。不含隐藏效果、秘密事实正文或规划器判断。表达器等待所有影响该决策的旁白与角色单元通过审批，不依赖尚未展示的后续内容。

刚获批、将同包展示的台词可作为本次选项的临时上下文，标明说话者、确定程度和来源。它尚不代表永久玩家知识已写回，更不能把 NPC 声称的内容提升为真相。

输出严格为两个 candidateId 与对应 label，不生成 Action、effect、分支或 token。候选一一对应，无缺失、重复或额外项。若对白无法自然承接批准的候选，拒绝并回退修复相应上游阶段，不能悄悄改动作语义。

### 8.2 纯对白规范

所有玩家对白选择只显示玩家准备说出的原话：

- 禁止“顺着她的话头接一句：”“盯着她问：”“试探地说：”等前置说明。
- 禁止括号动作、心理活动、第三人称描述、说话人标签和结果预告。
- 不添加外层引号、AI 生成的序号或装饰性 `>`；UI 的统一选择标记属于界面，不属于 label。
- 不限制自然对白自身使用冒号或疑问句，不能以标点规则误伤合法文本。
- 禁止以“温和/强硬”等标签代替实际策略差异；语气必须与获批意图一致。

示例：合格的 label 可以是“你先告诉我委托人是谁，我再决定接不接。”；不合格的是“谨慎地试探：你先告诉我委托人是谁，我再决定接不接。”。示例只说明表达形式，不能作为生产默认文本。

审批检查纯对白格式、上下文承接、玩家知识权限、候选语义对应和两条策略的可辨识差异。格式不合规要求模型修复，不通过截断冒号前内容等规则加工冒充生成成功。

对白中的“我会交钱”“我去找他”可以表达承诺或意愿，但必须与批准候选的即时语义一致；不能把一句承诺映射成已经支付或已经抵达。反之，不能让标签承诺一项规则不支持的实际效果。不同策略可以有未知后果，但玩家从 label 和已展示场景中必须能理解自己选择的目标与做法。

### 8.3 入口与例外

普通焦点 NPC 决策保持两个固定回应和一个自定义输入。缺少正式场景时的 ask 是开始生成的入口，不冒充两条已批准对白。交接确认和地图/物品/战斗按钮属于操作 UI，不强制改成对白。

终幕若以玩家说话呈现，其 label 也遵守纯对白规则；两个立场和结局资格仍由既有规则确定，表达器不能改写。终幕表达应在结局包发布前完成，客户端点击立场时不增加生成调用、不开放自由输入。不得为满足普通分支要求擅自新增结局规则。

## 9. 状态、发布与失败恢复

生成任务保存 jobId、baseRevision、阶段、生成单元身份、各单元输入摘要、获批产物版本、依赖关系、失败原因和尝试次数。区分任务状态与游戏状态：规划获批、旁白完成、角色完成、选项完成均属于生成进度，不等于事件已发生。

内部产物可持久化，但不进入客户端 read model，也不建立第二份权威事实来源。新实体的批准、玩家可见释放、行动执行和知识获得必须分开。背景事实可在整包发布时按规则建立；未来事件及行动后果只在实际消费时提交。

必要阶段全部通过后，一次 CAS 提交当前场景、choice registry、批准的世界结构、bundle、当前确实发生的事件和由账本重建的记忆。未来 scene 不提前记录为 presented。已提交的玩家规则回合在生成失败时保留。

知识传播同时依赖实际消费事件、受众和最终获批表达：骨架要求透露某事实，但最终对白没有实际披露时，不得仍按规划给受众写入知识，必须拒绝不一致产物并修复。听到 NPC 的未证实陈述只产生带来源和确定程度的认知，不将其提升为世界真相。

并发与恢复要求：

- 同 job/生成单元/输入版本只允许一个有效生成任务；独立单元可并行，轮询不能重复付费启动。
- 重启后能恢复获批阶段；以输入与规则版本摘要判断产物是否可复用。
- 下游失败只重试失败单元；上游修改会使所有依赖它的下游产物失效，不重做仍有效的独立旁白或角色单元。
- 选项表达失败先重试表达；若确为骨架语义与对白冲突，明确失效并重做依赖链，不能无限来回修复。
- 规则 revision 或依赖变化时禁止旧结果覆盖新状态；失效任务按原业务边界恢复，不增加移动/战斗的生成触发。
- 每个逻辑生成单元在一次尝试周期内最多四次完整内容尝试；输入版本改变不重置其累计次数。基础请求数按第 3 节的生成单元计算，不使用固定十二次上限限制所有规模的包。实施 Plan 必须明确基础单元数上限、额外内容请求额度和任务总耗时上限，并落实为有界配置；规划审批时验证整包基础工作量可容纳，不能批准正常成功路径就超预算的骨架。修复重试及上游重做引发的下游再生成都消耗额外额度；骨架改版或单元改名不能重置任务预算。传输重试独立受限、单独计数，耗时计入任务总耗时。达到任一上限即失败。
- 手动重试沿用同一逻辑 job，重新开启一次有界尝试周期并保留审计记录；可复用输入仍有效的获批产物。
- 开局也受分阶段约束，整包完成前不创建半成品游戏；场景失败保留同任务的失败状态。生产不得使用固定文本、旧单次 source 或 fixture 兜底。

初始化任务必须能独立于尚未创建的 GameRecord 持久化，保存稳定 jobId、输入摘要及有效产物；创建请求需有幂等身份，重发或失败重试不能悄悄创建新任务重复计费。显式修改开局输入或选择重新生成才创建新任务并使旧任务失效。完整包发布时再原子创建游戏及 current 指针；若是结束后重开，失败前保留原游戏。现有依赖当前存档的 narrative/ensure 不足以自动覆盖此场景，实施须明确初始化任务的查询和重试接口契约，但不把它算作新的剧情业务触发类型。

任务总耗时从尝试周期启动起计算，包含依赖等待、内容生成、传输重试和在线审核；同时设置并行请求上限。取消、超时或输入失效时停止调度下游并尽可能取消在途请求，迟到响应不得发布或继续派生任务。provider 已接收请求后可能仍计费；本地去重和恢复不能保证远端恰好执行一次。重启后对结果未知的在途单元记录明确状态并计入已用预算，支持 provider 幂等键时复用，不以预算重置掩盖重复请求。

## 10. 上下文、审计与客户端

四类生成职责分别设置输入/输出 token、超时和重试预算，不以统一大上下文替代裁剪。必需事实超过预算时明确失败，不能静默丢弃依据。各类生成可以使用同一个模型，但不能继承其他单元的完整会话历史或共享未经裁剪的缓存；仅通过服务端批准的权限投影传递依赖内容。

审计能关联 job、阶段、生成单元、speaker、step、revision、产物版本、输入摘要、内容尝试与传输尝试。记录每单元延迟、请求次数、拒绝原因、依赖等待和发布结果；明确区分逻辑一次生成与实际 provider 请求数，并区分基础生成、内容重试和额外模型审核。

审计正文按已有敏感产物政策保存，不能因导演信息更广而进入普通日志或客户端。修复上下文使用本阶段授权范围内的拒绝原因，不回传包含秘密的跨阶段原始输出。

客户端保留生成中与显式重试体验，只显示完整批准内容。可以显示笼统生成进度，不暴露骨架、内部候选、角色知识白名单或隐藏后果。生成完成不得自动跳过玩家当前阅读内容。

## 11. 验收要求

| 场景 | 必须证明的结果 |
| --- | --- |
| 单 NPC 普通决策 | 一个旁白单元、一个角色单元、一处决策且无重试或额外审核时，恰好规划、旁白、表现、选项四次独立请求；只有最终完整包可见 |
| 输入隔离 | 捕获实际请求，证明旁白请求不含完整骨架、隐藏动机或未来安排；角色请求不含完整骨架、隐藏后果、他人私密正文；选项请求不含玩家未知内容；修复请求同样满足隔离 |
| 固定职责分离 | 规划器不生成最终旁白，角色请求不附带旁白；即使同场且素材均安全，旁白仍独立生成 |
| 玩家与 NPC 视角 | 玩家可见、NPC 不可见的事件只进入玩家视角；NPC 已知但玩家尚未获知的内容不提前进入旁白；旁白不将隐藏动机叙述为事实 |
| 表达依赖与顺序 | 独立环境旁白和角色单元可并行；依赖角色动作的旁白等待其审批；反向环境依赖使用 NPC 可观察投影；无循环依赖，装配不受请求完成顺序影响 |
| 实际信息传播 | 计划披露但对白未披露的事实不能写入受众知识；获批动作被旁白引用后不产生重复后果 |
| 多单元预算 | 多 NPC、多个旁白和连续步骤的基础调用数按实际单元核算；超出配置的骨架在审批时拒绝；重试、改版和下游重做均受累计预算限制 |
| 同世界不同 NPC | 甲未知、乙已知的事实只进入乙的授权上下文；不能由共用记忆或修复提示泄露 |
| 知道但不可说 | 秘密正文不进入演员请求；正文也不能披露其含义 |
| NPC 说法 | 未证实陈述保持来源与不确定性，不自动铸造成世界真相 |
| 未来认知 | 远处 NPC 不知私聊；实际传播或见证成立后才可表达相应知识 |
| 纯对白 | 无小说式前缀、舞台动作、心理说明或效果预告；合法对白中的标点不被错误拒绝 |
| 两条分支 | 从同一批准状态分别执行两个 token；本次或下一决策前出现可观察、规则可证明的差异及因果记录 |
| 假分支 | 不同措辞、相同结果，或只有无后续意义的数值微差，均不通过 |
| 意图与结果 | 拒绝、承诺、自由文本不能自动移动、送物、支付或判胜；只提交规则支持的后果 |
| 条件消费 | 胜利对白不在失败路径出现；无效前提、旧 token、过期 revision 零越权写入 |
| 正常回合推进 | 预期行动导致 revision 增加后，依赖仍成立的未来步骤可消费；依赖被破坏时拒绝，不能将所有 revision 变化视为失效 |
| 结构化表演动作 | 停顿等表演可审批后交旁白表达；表演说明不直接展示，不凭空新增线索或修改情绪等持久状态 |
| 重试与重启 | 下游失败复用有效上游；上游修改失效下游；无重复事件、选项或知识传播 |
| 初始化任务恢复 | 无 GameRecord 时仍可查询和重试同一失败任务；重复创建请求不产生多个有效任务，只有完整包创建游戏 |
| 超时与迟到响应 | 任务停止后不调度下游、不发布迟到结果；重启恢复不清空已用预算或掩盖结果未知请求 |
| 发布原子性 | 任一阶段失败都不发布半包；保留已提交的规则回合和稳定失败身份 |
| 开局与终幕 | 首轮无固定 support/challenge 文案假分支；终幕只表达规则已确定的合法立场 |

确定性测试覆盖状态、权限投影、依赖、规则和提交；真实 AI 验收覆盖旁白与台词泄露、语义承接、纯对白与选项策略差异。测试集包含秘密诱导、多个 NPC、玩家与 NPC 观察范围不同、旁白与角色相互承接、跨地点、战斗条件、跨幕和开局续接，不只检查模型自报引用。

真实验收报告必须保留全部请求与失败样本、实际调用数、延迟及人工逐条判断；不能用离线 fixture 通过证明真实文本质量，也不能删掉失败样本后声称无泄露。本文不保存测试成绩。
