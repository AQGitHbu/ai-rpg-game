# RPG 游戏开发规范

> 本文档规定 RPG 项目的代码放置、依赖方向和验收方式（HOW）。跨项目稳定规则见 `共同规范/共同游戏开发规范.md`；玩法与玩家可见规则见 `策划文档/`。
>
> 最后更新：2026-08-11

## 0. 使用与维护

- 新增或调整实现前，先定位它属于 `domain`、`core`、`gameplay`、`application` 或外部入口；不能仅因文件方便而跨层放置。
- 本文只记录 RPG 的路径、现状和例外，不复制 `共同规范/` 的内容。共同规范是 foundation 的同步副本，禁止在本仓直接修改。
- 新模块必须有同目录测试；新增跨层 import、facade 或 server 入口时同步更新 `src/dependencyBoundaries.test.ts` 并运行 `npm run test:boundaries`。
- 当任务涉及 `@ai-game/*`、通用 UI/AI/日志/测试配置或无 RPG 业务语义的基础模块时，按根 `AGENTS.md` 读取共享模块流程；一次产品需求不能据此预建共享包。

### 0.1 环境准备

- 本仓文档大量使用中文文件名。克隆或新建 worktree 后，在仓库内执行一次性本仓配置：`git config core.quotepath false`（仅写入当前仓库 `.git/config`，不修改全局配置）。
- 该配置让 `git log --name-only`、`git diff --stat`、`git status` 等管道输出以可读 UTF-8 形式呈现中文路径，而不是 `"docs/\346\270\270..."` 式八进制转义；历史分析、变更统计等基于 git 输出的工具因此可以直接按路径匹配文件，无需先反转义。
- 适用范围仅限本仓（含其 worktree，worktree 共享主仓 `.git/config`）。不要求也不建议改全局 `core.quotepath`。文件命名策略不变，中文文件名继续按现状使用。
- 当前 `scripts/` 下自研脚本只消费 `branch`、`rev-parse`、`worktree list` 等非文件路径输出，或仅判断 `status --porcelain` 是否为空，不解析具体文件路径，无需兼容转义/非转义两种路径形态；未来若新增解析 git 文件路径输出的脚本，应在子进程调用中显式传 `-c core.quotepath=false`，不依赖仓库配置。

### 0.2 分支合并与 worktree 收尾

- 功能分支必须从本仓主工作区执行统一入口：`npm run branch:merge -- <branch>`，例如 `npm run branch:merge -- codex/real-playtest-20-turns`。该入口会检查 `main` 与目标 worktree 均干净，执行 `git merge --ff-only`，再委托 `branch:finish` 完成收尾。
- `branch:finish` 的固定顺序是：确认当前是干净 `main` → 确认目标本地分支是 `main` 的祖先 → 按分支名定位 `.worktrees/<name>` → 对已登记 worktree 委托 foundation 的受保护清理器 → 对工具失败后留下的目录仅在 junction 已解除、Git 登记已解除、目录内零链接时受控清理 → `git worktree prune` → 使用 `git branch -d` 删除分支。
- `branch:merge` 只允许 fast-forward 合并，不会自动创建合并提交；合并失败时保留分支和 worktree，必须先人工处理原因。已完成合并但只需清理时，仍可单独执行 `npm run branch:finish -- <branch>`。
- 脚本默认拒绝 main 或 worktree 有未提交修改、未合并分支、路径不在本仓 `.worktrees/`、以及 foundation 不完整的情况；不提供 `-D`、递归删除 junction 或跨仓清理选项。
- Windows 清理前必须退出该 worktree 中的 dev server、测试 watcher、终端和其它进程。若出现 `EPERM`，脚本会保留无法删除的现场并报告精确路径；不得改用 `git worktree remove`、`rm -rf` 或扩大删除目标。
- `npm run worktree:remove -- <name>` 仍是只删除 worktree 的底层快捷入口；日常合并后的完整收尾优先使用 `branch:finish`，避免手工串联合并检查、worktree 清理和分支删除。

## 1. 分层与依赖

### 1.1 目标结构：core + gameplay + app

RPG 采用“稳定数据语言 + 可选通用机制 + 产品规则 + 用例编排”的结构：

```text
components / store / app page     app/api route
           │                         │
           └──── application facade ─┘
                         │
                 gameplay/rpg facades
                         │
                 domain types / pure helpers

application/server composition root → SQLite / AI provider / environment
core（出现真实通用机制时）→ 被 gameplay 或 application 使用，不认识 RPG
```

`core` 不是把目录凑成三层的理由。只有出现至少一个可复用、无 RPG 词汇的机制（例如行动调度、事件账本、通用持久化事务工具、可取消任务协调）时，才创建 `src/game/core/` 模块。它必须有独立 public facade、同目录测试和专门的 boundary guard；不得 import `domain`、`gameplay`、`application`、`components`、`store` 或 `app`，也不得包含地点、NPC、任务、战斗、叙事、存档业务字段或 prompt。

`domain` 保持稳定的 RPG 领域语言与纯函数；`gameplay/rpg` 负责意图校验、规则裁决、状态转移和结构化事件；`application` 负责用例、read model 和请求适配。外部入口只能消费 application 暴露的命令、结果和视图。

### 1.2 当前符合度

| 范围 | 当前状态 | 结论 |
| --- | --- | --- |
| `src/game/domain/` | 已有稳定类型、ID、`GameState` 与纯辅助函数；边界测试禁止反向依赖。 | 已符合。 |
| `src/game/gameplay/rpg/` | 已有场景、行动、任务、战斗、叙事和小镇规则，并以子系统 facade 对 application 开放。 | 已符合。 |
| `src/game/application/` | 已有 use case、read model、请求适配与公共 `index.ts` facade。 | 已符合。 |
| `src/game/core/` | 当前没有生产模块。 | 尚未实现；不得把现有 RPG 代码为“对齐三层”而机械搬迁。 |
| `src/game/logging/` | 已有纯 facade、递归脱敏和 server console sink；composition root 注入至 AI、SQLite 与后台任务。 | 已符合，见 4.3。 |

因此，当前项目已落实 domain → gameplay → application 的主要边界，但尚不是已落地的完整 core + gameplay + app 三层实现。后续新增机制遵守本节准入条件；不以空 `core` 目录作为完成标志。

### 1.3 Facade 与 import 规则

- UI、store、页面和 API route 只从 `@/game/application` 导入游戏能力及类型；不得直连 `@/game/domain`、`@/game/gameplay/**`、SQLite 适配器或 application/server 私有模块。
- application 通过 `@/game/gameplay/rpg/<system>` 的 `index.ts` facade 调用玩法。不得 deep-import `actions`、`quests`、`battle`、`narrative`、`scenario` 或 `town` 的内部文件。
- gameplay 可依赖 `@/game/domain` 和未来的 `@/game/core/<system>` facade，但不得依赖 application、UI、store、API、provider、数据库或 `server-only`。
- `application/server/` 是唯一允许装配真实 provider、数据库客户端、环境变量和密钥的层。API route 只能使用 `@/game/application/server/compositionRoot`，不直接装配依赖。
- 客户端可达 facade 不得 re-export server-only 能力。类型转发也必须保持浏览器不需加载 provider、文件路径或环境变量。

## 2. Application 与外部入口

### 2.1 application 的三种职责

| 职责 | 放置位置 | 例子 |
| --- | --- | --- |
| Use case | `src/game/application/` | 创建游戏、执行行动、生成待处理叙事或小镇计划。 |
| Read model | `src/game/application/` | 将 `GameState` 投影为 `GameSessionView`、地图或小镇视图。 |
| Request adapter | `src/game/application/` | 封装浏览器请求与稳定的命令/错误映射。 |

application 可以编排玩法 facade 和 domain 类型，但不在此重新裁决行动合法性、数值、掉落、任务或胜负。若 UI 需要新展示事实，优先新增 read model，不向领域状态添加仅为样式服务的字段。

当前生产 application 只有一条无版本后缀的运行链：`createGame`、`performTurn`、`generatePendingScene`、`projectGameSessionView`、`GameRepository` 与 `compositionRoot`。不得新增带版本后缀的文件/导出、并行 use case、兼容 facade 或 read-model adapter；需要破坏性调整时直接修改这条链并同步测试与文档。

### 2.2 UI、store 和 API

- `src/components/` 只负责展示、交互局部状态、可访问性和把 application view 组合成 RPG 界面；不得从表单或文案反推 `GameState`，也不得改写规则结果。
- `src/store/` 只保存客户端会话、请求和展示状态；服务端权威状态必须由 application/API 返回的结构化 view 驱动。
- `src/app/` 的页面与 route handler 是输入/输出适配器。route handler 校验传输载荷、调用 composition root，并映射 HTTP 状态；它不包含玩法、SQL、prompt 或密钥逻辑。
- 玩法缺口由 gameplay 设计和实现解决，不在组件中临时补规则。
- 游戏 API 只有六个 route：`/api/game`、`/api/game/current`、`/api/game/actions`、`/api/game/narrative/ensure`、`/api/game/prologue/ack`、`/api/game/dev/current`。禁止版本化 route、重定向或兼容 endpoint。
- 固定 choiceToken 与 NPC 自定义输入只允许经 `/api/game/actions` 进入 `performTurn`；客户端每次提交产生独立 UUID，不能按 NPC 或按钮复用 action ID。
- UI 只消费 `GameSessionView` 下发的 opaque token，不生成/解析 token，不读取 `actionKey`，不将 Action、registry 或隐藏事实暴露到浏览器。

### 2.3 共享 UI

- `Panel`、`InlineButton`、`Tag` 只能从 `@ai-game/ui` package 根入口导入，禁止 deep import 或在 RPG 内复制其实现。
- 共享 package 负责无业务语义的结构、可访问性和稳定 class contract；RPG 主题 CSS 位于 `src/app/globals.css`，业务组合位于 `src/components/`。
- 新游戏表单、对白布局、角色立绘、streaming、地图、HUD、小镇和场景状态都是 RPG 业务，不进入 foundation。
- `TabBar`、Surface/Modal 等尚未成为共享 API；只有两个产品存在同语义的真实需求后，才按共享流程扩展。

## 3. 持久化与配置

### 3.1 存储边界

- `GameRepository` 是 application/server 使用的端口；当前 SQLite 实现在 `src/game/application/server/persistence/`，只有 `sqliteClient.ts` 可以 import `@libsql/client`。
- `src/game/application/server/compositionRoot.ts` 是生产依赖装配点：读取环境、创建 SQLite client/repository、生成 ID/seed/时钟并注入 use case。UI、store、API 及 gameplay 均不得看到数据库路径、client 或 SQL。
- 存档写入必须保持原子性、版本迁移和 compare-and-swap 语义；读取损坏或未知未来 schema 必须安全失败，不能自动重置玩家存档。
- 当前 SQLite 只使用 `game_records` 与 `current_game`。本次运行时收口是开发期破坏性重建：旧本地存档不迁移、不复制、不提供兼容读取；开发者清档后重开。schema/record 版本字段仍是持久化事实，不属于接口版本命名。
- 只有在存储机制完全无 RPG 状态语义且具有第二个真实消费者时，才按共享流程抽取。当前 `GameRecord`、存档 slot 和迁移仍是 RPG application/server 职责，不能仅因名称相同搬入 core 或 foundation。

### 3.2 开发工具与配置

- 开发环境清档是 server composition root 限制的工具能力。客户端只消费 current API 给出的可用性；`DELETE /api/game/dev/current` 必须在 server 端检查 `NODE_ENV === "development"`。
- 清档只能删除 current slot 指向的游戏行；禁止删除 SQLite 文件、schema、worktree、`.foundation` 或 sibling 仓库。
- 初始化模板、运行时 `GameState` 和仅展示数据必须分离。配置进入玩法前应完成结构与引用完整性校验；UI 不读取未校验的原始配置来决定规则。

## 4. AI 与日志

### 4.1 AI 的位置和责任

- `@ai-game/ai-transport` 只允许在 `src/game/application/server/ai/` 导入；它只提供请求、超时、取消和脱敏错误契约，不读取 RPG 环境变量，也不携带 RPG prompt、schema、重试或 fallback。
- AI runtime config、密钥、provider 调用、prompt 组装、输出解析和审计都在 `application/server/ai/`。密钥不进入 application facade、客户端 bundle、日志、测试快照或存档。
- AI 的候选必须经过类型、枚举、ID、长度、引用和越权校验；规则层仍裁决行动和状态变化。每个失败路径必须返回稳定分类并使用确定性 fallback，不能阻塞可完成的主流程。
- `traceId` 必须从一次异步请求贯穿候选、重试、审计和最终结果；record/replay fixture 只能保存脱敏、可复现的请求事实。

### 4.2 AI 测试

- prompt 测试验证允许的结构化上下文和敏感字段排除；不得以真实密钥或完整生产 prompt 快照作为 fixture。
- source 测试覆盖成功、超时/服务异常、不可解析输出、越权引用、重试上限和 fallback。
- 真实 AI smoke 只通过明确的环境门禁运行，不替代 fixture 和确定性完整旅程回归。

### 4.3 日志与追踪

- `src/game/logging/` 的根 facade 导出 `GameLogger`、`createGameLogger` 与 `NOOP_GAME_LOGGER`；真实 console sink 仅位于 `serverConsoleLogger.ts`，且只能由 server composition root 导入。
- 新增可观测性通过 `GameLogger` 注入，不能直接调用 `console`。日志事件至少包含事件名、稳定结果分类和必要耗时；请求关联场景在遥测契约允许时记录 `traceId`，只记录白名单字段。
- 禁止记录 API key、Authorization、cookie、完整 prompt、模型原文、未脱敏玩家输入、数据库连接字符串或完整存档。异常文本仅在 server 端按脱敏策略记录，不能回传给客户端。
- logging 是跨层基础设施：业务代码只从根 facade 导入，内部 sink/redaction 文件不对外；它不得 import RPG gameplay 或 application。`src/game/logging/dependencyBoundaries.test.ts` 禁止所有生产直连 console（唯一 server sink 例外）并守卫此依赖方向。

## 5. 测试与变更验收

- 纯 domain、core 和 gameplay 逻辑：同目录单元测试覆盖合法路径、非法输入、边界值和确定性结果。
- application：测试 use case 编排、read model 和稳定错误码；server adapter 通过注入 repository、时钟、ID、AI source 与日志端口测试，避免真实环境依赖。
- UI：组件测试覆盖展示状态、交互入口和错误文案；页面/API 测试验证只能经 application facade 到达游戏能力。
- 架构修改先补或调整边界测试，再改 import。新增 core 后，将现有 `src/dependencyBoundaries.test.ts` 的规则拆分或补充为 core 专项守卫，确保 core 的依赖白名单可执行。
- 最低验收：`npm run test:boundaries`、`npm run typecheck`。涉及现有快速门禁覆盖的改动运行 `npm run test:fast`；涉及共享 package 或跨仓修改时按共享模块流程运行对应合同与 `ready:family`。

### 5.1 面向变更的行为测试入口

改动核心热点时优先运行对应模块子集入口，而不是全量 `npm test`；子集通过后再按需跑全量。`npm run test:fast` 语义不变，仍是静态门禁（standards/typecheck/boundaries 等），不包含这些行为测试子集。

| 热点文件/目录 | 测试入口 |
| --- | --- |
| `src/game/domain/**` | `npm run test:game-domain` |
| `src/game/gameplay/rpg/**`（actions/quests/battle/narrative/scenario/town） | `npm run test:game-gameplay` |
| `src/game/application/**`（use case、read model、server/ai、server/persistence、journey 回归） | `npm run test:game-application` |
| `src/game/logging/**` | `npm run test:game-logging` |
| `src/components/**` | `npm run test:components` |
| `src/app/**`（页面与 API route handler） | `npm run test:app` |

跨层改动（例如 domain 类型变化波及 application 与 UI）用变更感知入口：

- `npm run test:changed`：基于 git 未提交变更，运行受影响的测试（vitest `--changed`）。
- `npm run test:related -- <文件路径...>`：显式指定源文件，运行 import 链上相关的测试（vitest `related`）。

以上入口只是运行范围裁剪，不改变测试内容与断言；合入前的完整验收仍以第 5 节最低验收和全量 `npm test` 为准。

## 6. 当前玩法脚手架约束

- 当前正式状态模型为 `WorldState + StoryState`，并具备确定性 fallback、SQLite CAS 存档、固定选择、焦点 NPC 自定义输入、移动、探索、物品取得、任务 reconciliation、确定性战斗、失败分支和多结局。新代码必须建立在已编译世界与 application facade 之上，不得从 UI 表单或生成文本自行推导领域事实。
- 每个焦点 NPC ready scene 必须下发两个语义不同的固定选择并开启一个自定义输入；成功选择产生一个 `TurnResolution`、一个 `PendingNarrativeJob` 和一次规则 CAS。AI/fixture 只提 proposal，审批后 scene 与 choice registry 用独立 narrative CAS 写回。
- 正式产品时长只开放短篇/中篇。长篇/开放式支持需要先完成 segmented ledger Spec/Plan；当前 UI、文档和产品文案不得声称无限时长、无限扩张或无限记忆。
- 完整旅程门禁必须证明至少 15 个成功回合、跨 reload、固定与自定义 NPC 选择、世界/候选事件推进、战斗和结局；分叉门禁必须证明同 seed 不同选择得到不同结构化状态和不同结局方向（trust/doubt 由规则要求按关键 NPC 亲和度裁决，离线可达）。
- 新玩法或系统先按对应 Spec/Plan 建立，再写实现；玩法事实变化同步更新 `docs/策划文档/`，实现事实变化同步更新 `docs/agent/` 和 `docs/Agent文档索引.md`。
