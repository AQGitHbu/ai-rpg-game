# 共享模块开发流程

> 仅当项目根 `AGENTS.md` 的共享基础设施触发条件命中时阅读。

## 公共仓库定位

- 公共仓库名：`ai-game-foundation`。
- sibling 主仓默认路径：相对游戏主仓解析 `../ai-game-foundation`。
- 项目根 `.ai-game-foundation.json` 是 agent 和脚本的机器可读定位文件；其中路径必须使用相对路径，不能提交个人机器的绝对路径。
- 如果仓库不在默认 sibling 位置，使用 `AI_GAME_FOUNDATION_DIR` 覆盖本地路径。
- `.foundation` junction 与 Next.js 本地联调要求游戏和 foundation 位于同一文件系统；跨盘/跨文件系统时应使用 registry package，不用绝对路径绕过。
- 游戏位于 `.worktrees/<name>` 时，locator 通过 Git common dir 找到游戏主仓，并优先选择 foundation 的同名 `.worktrees/<name>`；不存在时才回退 foundation 主仓。
- 本地 package 通过项目内被忽略的 `.foundation` junction 暴露为稳定 `file:.foundation/packages/<package>` 路径，禁止把 worktree 绝对路径写进 package.json 或 lockfile。
- registry 尚未启用时，共享 package 的确定性 `dist/` 随 foundation 提交；消费者的 `setup` 只建立 `.foundation` 链接并安装自己的依赖，禁止从消费者脚本对 foundation 执行 `npm ci` 或 build，避免多个项目并发写同一目录。
- 修改共享 package 的 agent 必须在 foundation 自己的 worktree 执行 install/build/test，提交源码与更新后的 `dist/`，再运行两个消费者合同；消费者不能依赖另一次开发遗留的未提交产物。
- 提交共享 UI 前运行 `npm run verify:ui-dist`；命令会重新构建并拒绝未纳入提交的 `dist/` 变化。
- `docs/共同规范/` 是已提交的消费副本，权威源始终位于 foundation；禁止直接修改同步副本。
- registry 发布后，代码依赖使用精确版本；本地仓库路径只用于修改公共源码、发布前联调和尚未发布时的 bootstrap。

## 决策

1. 已有 `@ai-game/*` package 覆盖职责：先修改 foundation，再升级当前项目。
2. 新能力第一次出现：在当前项目实现，保持 facade、测试和清晰边界。
3. 第二个真实消费者出现：比较输入、输出、错误语义和依赖；只有交集稳定且无产品概念时抽取。
4. 名称相同但规则或状态语义不同：继续分别维护。

## 抽取前提

- 两个生产项目真实使用；
- 公共实现不 import 任一项目 domain；
- 有 public API、独立测试和两个消费者 contract test；
- 新版本使用精确版本号；
- 发布前用 prerelease 验证两个消费者。

## 发布顺序

```text
foundation 分支
→ package 测试
→ prerelease
→ 两个消费者契约测试
→ stable release
→ 各项目按需独立升级
```

公共新版本不会影响未升级的消费者。禁止 `latest`、`*` 和 deep import。
