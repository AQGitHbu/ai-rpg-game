# 世界动态具象化

## 系统定位

开局只生成一个可完成的开局切片：故事契约（幕数、中心冲突、两个抽象结局方向）、世界前提、玩家、序幕、一个起始地点、一名开场 NPC、一条活动主线与开场事实。不再生成完整的未来实体蓝图。运行时世界演化只在剧情需要且预算允许时按需具象化新地点、NPC、物品、敌人、下一幕主线或结局对；所有候选先审批再写入，保证每局有变化但仍可完成。

## 正式支持范围

- 产品 UI 只开放 `short`（短篇）与 `medium`（中篇）。
- 开局只铸造 `loc_0` / `npc_0` / `quest_0` 与开场目标所需事实；不命名或持久化未来 NPC、地点、任务、敌人或具体结局。
- 短篇与中篇分别使用有界主线幕数和软顶预算；到达终幕、达到软顶/硬顶或预算边界后停止扩张。
- 长篇/开放式在 segmented ledger 专项 Spec/Plan 完成前不属于正式产品能力，不得宣称无限扩张或无限记忆。

## seed 与每局差异

- 同一输入与同一 seed 生成相同规则结构，支持确定性 reload/replay。
- 不同 seed 进入开局生成上下文；生成候选必须通过近期开局指纹相似度校验，改变场景框架、NPC 功能、线索类型或冲突方式，而不只是改一段文案；回归至少比较这些结构标签与地点/NPC/任务组合。
- 玩家选择在同一 seed 内继续造成结构化分叉：关系、NPC 情绪/历史、候选事件、可达路线和结局都可不同。
- seed 不绕过类型、引用完整性、预算、任务可达性和双结局校验。

## 世界演化闭环

```text
开局或正式 NPC provider job
  → deriveEvolutionNeed（none | next_act | pacing | ending_pair）
  → 仅 need !== "none" 时调用演化源
  → WorldDeltaProposal（纯字符串引用）
  → approveWorldDelta（类型、ID、引用、预算、节奏、收束、结局对）
  → materializeWorldDelta（服务端铸品牌化 ID、装配预览状态）
  → 与场景写回同一受控 CAS 原子持久化
```

## World Prompt 编译器（2026-08-23）

- `liveWorldEvolutionSource` 现在只通过 `compileWorldNarrativeContext(context)` 生成 Prompt；world Prompt 的唯一 schema/块定义来源是 `src/game/application/server/ai/narrativeContext/contextBlock.ts`、`worldNarrativeContext.ts` 与 `renderNarrativeContext.ts`。
- world 编译块会投影：世界/题材规则、故事契约、当前 act/targetActs/storyProgress/tension/budget、当前地点与 placement 规则、已批准实体索引、当前演化 need/reason/安全 action 摘要、公开事实、附近实体细节与过滤后的 recent beats。
- world 编译块明确不投影：`eventLedger`、NPC 私密记忆正文、`hiddenFactIds` 对应事实正文、未发现事实文本、玩家自由输入原文、裸关系数值，以及不在已批准实体索引中的旧 ID。`freeform.rawText` 和 intent parser 输出都不会进入 world Prompt。
- 本阶段只替换 world Prompt 的上下文装配；world 演化仍保持原有一次 source 调用、一次审批/内容修复循环和同一次 scene CAS 写回，不增加额外 AI 调用，也不引入存档 schema 迁移。

- `StoryEvolutionState` 持久化 ID 铸造序号（location/npc/item/enemy/fact/quest/ending ordinal）与状态（`stable` / `needs_next_act` / `needs_ending_pair`）。
- 演化需求纯领域派生：幕完成 → `needs_next_act`，节奏低 → `pacing: complicate | escalate`，终幕 → `needs_ending_pair`；线性动作返回 `none`，不调用演化源。需要演化时只在允许的 opening/NPC provider job 内调用。
- 未知实体引用回合可走修复路径：把行动引用 ID 原样铸造为缺失实体（kind 对齐），再以预览状态重演算；成功则单次 CAS 提交。
- 动态地点提案必须显式声明空间归属：`placement: "world"` 才会铸造新地点、建立双向连接，并由当前主线首个 `visit_location` 目标立即解锁；`placement: "town_building"` 表示当前城镇内部的茶馆/酒楼/宅院/后巷等建筑，不铸造 `LocationEntry`、不进入世界地图，而是要求 `newNpc.locationRef = new_location`，把 NPC 绑定到当前城镇第一个空闲剧情建筑 slot，并使用提案地点名作为建筑展示名。城镇建筑必须位于当前 `scale: "town"` 地点且有空闲 slot；满槽或引用不合法时审批拒绝。若同批创建 world 地点与事实，目标链固定先 visit 再自动确认事实，事实 `locationId` 必须与新地点一致。NPC/物品/敌人必须挂到有效地点索引。
- 世界演化可以一次生成同一幕的完整实体与顺序目标，但 `StoryState.reveal` 只释放当前目标及其实体；完成当前目标后只前移一个释放游标。未释放的地点、NPC、物品、敌人既不进入地图/read model，也不进入场景表演上下文，不能被旧 choice token 绕过。
- 终幕只按故事契约的两个抽象方向（trust/doubt）铸造一对互斥结局；结局达成条件由规则按关键 NPC 亲和度派生，AI 不能提交或覆盖 requirements，不存在预生成的隐藏任务图。
- live proposal 传输、解析或语义审批失败时返回稳定 `AI_CALL_FAILED` 或 `AI_RESPONSE_INVALID`，零演化写入；pending 场景保留原 job 并进入 failed，玩家可手动重试。确定性剧本按 `gameType` 索引（7 题材库，acts 2-5，超出回落通用模板）只由显式 offline fixture 使用；`investigationLabel` 由节拍携带。
- live 世界演化提示词按 `EvolutionNeed` 条件化字段合同：`next_act` 必须带 `nextMainQuest` 且省略 `endingPair`，`ending_pair` 才允许输出结局对，`pacing` 两者都省略，避免模型把下一幕提案误判为终幕。
- **world source 自动最多一次内容修复（2026-08-22）**：`evolveWorld` 用“初次提案 + 至多一次 content repair”两轮循环统一覆盖结构化解析失败与审批拒绝——source 解析失败时按稳定原因进入修复（`repairReason: invalid_json / invalid_schema / invalid_reference`），`approveWorldDelta` 拒绝时进入修复（`reason: approval_rejected`，并携带稳定 `approvalCode`，即 `WorldDeltaRejection` 之一）；第二轮仍失败统一持久化稳定 `AI_RESPONSE_INVALID`，零演化写入。`WorldEvolutionContentRepair.reason` 恰为 `invalid_json/invalid_schema/invalid_reference/approval_rejected` 四种（后三种可由 `sourceResult.repairReason` 或 `proposal===null` 触发）。传输失败、`unavailable` 与空响应**不进**此内容修复循环，由 `RpgAiClient` 按 `mechanism=transport` 处理或返回稳定 `AI_CALL_FAILED`。
- **新地点与主线目标空间一致由审批层硬拒绝（2026-08-22，2026-08-26 加强）**：`next_act` 的 `placement="world"` 主线新地点必须从玩家当前地点接入，且同批目标 NPC、物品、敌人必须使用 `locationRef={kind:"new_location"}`；否则在 ID 铸造/预算预占前即返回 `code=unreachable_objective`（内部 reason 分别为 `location_not_from_current`、`npc_not_at_new_location`、`item_not_at_new_location`、`enemy_not_at_new_location`）。不把新地点生成到只能回退绕行的旧节点，也不把主线实体留在旧地点；这类被拒绝的提案随后进入上一条的一次内容修复。
- **续幕提案的保守结构归一化（2026-08-26）**：live source 在审批前仅做两类不创造玩家文本的修正：与现有 NPC 同名的 newNpc 声明会被移除；共享 events 预算耗尽时会移除可选的 newItem/newEnemy/newFact。AI 生成的剧情正文、地点、任务和结局正文绝不由此替换或合成。续幕 Prompt 同时强制从当前地点接入一个 world 新地点、禁止提前宣告中心冲突已解决，并明确事件容量为零时不能输出上述可选字段；其余结构错误仍进入同一 job 的 retry，绝不 fallback。
- 调查方式的 `label/hint` 可以正常复用事实中的地点、人物和线索关键词；只有完整复制 `newFact.text` 才属于正文泄漏并拒绝提案，避免把正常的调查入口误判为 `invalid_schema`。
- 新地点装配只保留与既有连接点的边，不把自身或同批地点写成连接，避免地图出现“前往当前地点”的自环。
- AI 只提案；ID 铸造、引用解析、预算消费、任务与结局始终由规则负责。
- 当前城镇的剧情建筑槽位由服务端城镇状态计算并注入 world prompt；满槽时 prompt 明确禁止 `town_building`，要求独立新地点使用 `world`，且同批主线 NPC 的 `locationRef` 必须指向 `new_location`，避免 provider 返回 HTTP 200 后连续撞上 `town_capacity`/`unreachable_objective` 而落入 `AI_RESPONSE_INVALID`（2026-08-26）。

## 主要验收

- 开局恰一地点/一 NPC/一活动主线；同 seed 创建结果结构相等，不同 seed 的结构化世界至少一项不同。
- 首次对话后下一次叙事写回具象化新 NPC 与（地点或物品），下一场景提及已批准名称。
- 演化 proposal 的非法/越权/超预算引用被拒绝且零写入；source 失败零演化写入并让当前叙事进入 failed，等待同 job 手动重试。
- 复用、收束和预算耗尽可继续规则链；source 失败不伪造剧情成功，离线继续主流程仅属于显式 fixture journey。
- 完整旅程跨地点、候选事件、战斗抵达结局；同 seed 的不同选择抵达不同结局方向（trust/doubt），离线也可按玩家选择裁决。

## 修改注意事项

- 预算数值只从 domain policy 读取，prompt、validator 和 UI 不复制另一份事实。
- 不为未落地的长篇能力放宽 hard limit 或使用伪无限数值作为产品承诺。
- 新实体必须服务当前主线缺口、角色选择后果或可完成路线，不能成为无规则引用的背景填充。
- 不再恢复旧蓝图聚合、旧全量世界候选、旧 `expansion` 管线或旧 `town ensure` 路由。
