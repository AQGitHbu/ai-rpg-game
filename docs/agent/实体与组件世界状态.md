# 实体与组件世界状态

## 职责

`EntityStore` 是世界实体事实的唯一来源；`WorldState` 保留由 store 投影的兼容集合和不属于实体的运行时字段。解析、构造和持久化必须先验证 store，再使用投影。

## 当前契约

- SQLite 驱动为 Node 内置 `node:sqlite`，入口 `src/game/application/server/persistence/sqliteClient.ts`；仓储保持原子事务、revision/lease CAS 与重载校验，事务未提交关闭时回滚。更换驱动不更改游戏规则或放宽存档验证，开发验收使用独立新数据库，不建立旧存档迁移链。
- `EntityStore.version` 为 4；`WorldState` schema version 为 8，`StoryState` schema version 为 13。Entity4/World8 增加 Fact 的显式 `discoveryMode`、调查方式的 requirements/witnessNpcIds 与调查来源约束；Story13 固化结果边界 pending job 与 Bundle3 合同；旧版本不迁移、不清除已有存档，按 `UNSUPPORTED_RECORD` 拒绝。StoryState 保存正式 History、pending job 的 durable attempt 与递送角色绑定；递送契约存在时必须同时存在 `delivery`，其中 item/委托人引用已有实体，接应人具象化前为 null。SQLite 对已知旧版本返回 `UNSUPPORTED_RECORD`，未知版本返回 `VERSION_MISMATCH`。JSON/record 无法解析为 `UNPARSEABLE_RECORD`，当前结构、引用或 memory 漂移为 `ENTITY_STATE_INVALID`。
- entity kind 为 player、npc、location、item、enemy、faction、quest、fact。每个 kind 有固定组件集合；record 的 core keys、ID/kind 对应、lifecycle 和嵌套组件都必须 exact-key 校验。
- NPC 组件由 [NPC人格知识与关系图](./NPC人格知识与关系图.md) 约束；世界位置、任务、物品持有、战斗、结局和事件账本仍由各自规则/状态字段维护。
- player_character 有独立的 `knowledge.knownFactIds`；NPC 可选 `interactions` 只保存服务端已批准的故事互动定义。`EntityCore.aliases` 是带 `observerIds` 与 `evidenceEventIds` 的作用域称呼，不合并实体，也不从 legacy 投影猜造。
- `createWorldStateFromProjection` 是唯一组装点：编译 EntityStore，再由 `projectEntityStore` 生成 locations/npcs/items/quests 等兼容字段。生产写入禁止单独修改兼容数组。
- `eventLedger` 是 `CommittedNarrativeEvent[]`；实体组件中的 provenance 引用必须指向已提交事件，并满足顺序和实体存在性校验。
- 实体状态变更只能经 `src/game/gameplay/rpg/entityWorld/entityMutation.ts` 的 `applyEntityMutations` 细粒度 mutation 写入；`src/game/gameplay/rpg/entityWorld/proposedEntityCommand.ts` 的 `ProposedEntityCommand` 只负责解析、审批并转换为 mutation，目前没有接入 provider。
- NPC 目标只能通过 `set_npc_goal_status` 窄 mutation 改状态；可结算目标的 `resolution` 条款、事实调查、talk completion 和 NPC cooperation 只能通过 `approveStoryConsequenceBindings` 映射为四种封闭 binding mutation，重复同值幂等，冲突或已消费定义拒绝；互动定义只能通过 `install_story_interaction` 安装，条件失败时不得部分写入。
- `StoryCondition` 的 provider 提案只在 application 层经统一引用解析后保存正式 Fact/NPC/goal/promise ID；`goalOrdinal` 按当前 NPC goals 顺序解析，不能让模型伪造 goalId。绑定安装不生成玩家 Action、EventId 或知识，实际证据仍须走正式规则动作。
- Fact 的 `discoveryMode="investigation"` 必须绑定非空安全 label、scene location 和 2–3 个合法 approaches；witness 引用必须指向已存在 NPC。`discover_fact` 对该模式必须带匹配的 `investigationSource.approachId`，automatic 分支不得伪造来源。候选事件、故事互动和 NPC outward authority 不能在调查前披露或写入玩家已知事实。
- 战斗快照保存 entity store、event ledger 与战前 `NarrativeHistory`；失败恢复全部快照，避免失败行动和失败叙事进入永久连续性。

## 关键流程

```
SQLite JSON
  → parseEntityStore / validateEntityStoreStructure
  → EntityStore
  → projectEntityStore
  → WorldState selectors and gameplay rules
```

世界演化先审批 proposed delta，铸造实体 ID 和组件，再 materialize 到预览状态，最后由 application 的 bundle CAS 写回。任何未经审批的 provider 对象都不能直接进入存档。
