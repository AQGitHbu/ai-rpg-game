# 日志与追踪

## 职责

RPG 提供稳定日志 facade；foundation 的 `@ai-game/logging` 负责通用脱敏、事件校验、截断、SQLite/JSONL sink、查询和迁移。日志故障不能影响规则裁决、AI 结果或存档事务。

## 当前契约

- 业务代码从 `@/game/logging` 使用 `GameLogger`、`createGameLogger` 或 `NOOP_GAME_LOGGER`；只有 `src/game/logging/serverConsoleLogger.ts` 可以直接调用 console，且只由 composition root 导入。
- `compositionRoot` 创建同一日志运行时并注入 repository、AI source 与后台任务；HTTP route 透传安全 `traceId`，记录 started/completed/failed 和稳定结果码、状态、耗时。
- 普通诊断日志默认 SQLite `data/logs.db`，与游戏库分离；共享日志使用 Node 内置 SQLite，不加载 libsql 原生驱动。SQLite 不可用时写 `GAME_LOG_FALLBACK_DIR` 下的 JSONL。日志 sink 为 best-effort，`close()` 负责排空。
- 普通日志按字段名脱敏 API key、Authorization、cookie、token、密码、secret、prompt、原始请求/响应和模型输入输出；大事件按共享上限截断。业务日志只写白名单的事件名、稳定分类、revision、数量和必要耗时，不写玩家输入、完整存档或异常正文。
- AI 文本审计独立于普通日志：默认 full 保存 prompt、模型正文和最终文本；`GAME_API_AUDIT` 独立控制 API body。详见 [AI文本审计](./AI文本审计.md)。
- 日志上下文中的 retry 必须使用 `{origin, mechanism, attempt, reason}`；普通 ensure 轮询不重跑 failed job，`{retry:true}` 才标记 manual failed-job retry。provider transport attempt 与 content repair attempt 分开。
