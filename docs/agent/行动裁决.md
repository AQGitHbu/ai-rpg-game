# 行动裁决

## 系统定位

玩家提交选择或自然语言意图，规则系统决定“能否发生、发生什么”。固定选择与自定义输入都由 `performTurn` 编排，使用同一 Action union、同一任务/关系/知识/战斗/结局规则和同一次规则 StateCommit。

## 输入边界

- 固定选择：客户端提交服务器铸造的 opaque `choiceToken`；服务端只从当前 revision 的 registry 和当前合法行动重建 choice map。
- 自定义输入：客户端提交文本与焦点 NPC ID；服务端意图解析器将其转换为受支持 Action，不能把玩家宣称当成已发生事实。
- 客户端不提交 Action、`actionKey`、规则 effect、事实 ID 或候选事件 ID。
- 请求携带 `expectedRevision` 与每次新建的 `actionId`。非法、stale、重复或已经结局的请求不能留下部分写入。

## 当前 Action 能力

- `talk`：与在场 NPC 交谈，读取并更新统一 NPC 组件中的结构化 history、关系和知识边界内的事件。
- `explore`：观察/探索当前地点并产生结构化主事件。
- `investigate`：历史事实调查 action 的兼容形态；Action 可携带 `approachId`，但新 read model 不再铸造该 action 的 choice token。当前 discover_fact 由规则边界自动确认。
- `move`：移动到相邻且已解锁地点。
- `take_item`：拾取当前地点可获得物品。
- `attack` / `battle_action`：进入或推进确定性速度队列战斗；战斗行动支持攻击、技能、防御、撤退，目标由服务端 opaque token 绑定。
- `ack_prologue`：确认序幕，只能走受批准的固定选择。
- `freeform` 是服务端自由文本解析后的受控 Action 形态，不允许绕过规则写任意 effect。

没有规则实现的公开 action 不进入 Action union，也不能在 UI 中出现“以后再实现”的死按钮。

## Plan 3 NPC 后果裁决（待验收）

- 对话 signal、FactChange audience、赠物、明确 NPC 任务和共同战斗都通过 `EntityMutation` 写入同一个 `EntityStore`；没有明确参与者时不根据“关键 NPC”猜关系后果。
- 关系变化只能提交封闭 signal，由 `relationshipSignalPolicy` 计算四维 cap、stage/trend、evidence 和 commitment；请求不能携带 numeric delta、stage、evidence 或任意组件 patch。每个 NPC/target/action 最多产生一档且可幂等重放。
- `give_item` 只有需要回报的物品类型才开 debt，普通赠物不自动创建 promise/debt；任务只有 objective 明确指向 NPC 且该 NPC 参与本轮时才写对应 signal。`fought_together` 只给真实参战且胜利后的同伴。
- `performTurn` 对服务端铸造的 NPC `ask/talk` 入口保持权威：规则型场景或战斗后出现的非 registry 入口按正式 NPC provider 回合处理，不误走缺失 continuation 的线性路径；仍只产生一次规则 CAS 和白名单 pending。

## 调查行动裁决与自动揭示

- `investigate` 的显式方式校验仍服务旧存档/旧事件兼容；新玩家不会获得调查 token。历史方式字段不改变当前任务顺序，也不构成 UI 入口。
- `autoResolveCurrentInvestigation(worldState, storyState)` 是规则层纯辅助：当前主线首目标是当前地点的任意 `discover_fact` 时，返回一个自动 `fact_discovered` 结果；它不执行 quest reconciliation、不写 ledger、不创建 pending job。真正的事件、目标推进与 tension 写入仍在同一规则回合的 StateCommit 中完成，最多自动推进一个目标。
- 自动事件省略 approach/evidence/tension 元数据；旧事件读取时继续按既有兼容默认值处理。场景生成只消费已经结算的事件和目标结果；即时场景 write-back 是独立 narrative CAS，不能再次发现事实或修改 tension。

## 调查生成、审批与 fallback 边界

AI/fixture 可携带历史调查方式字段，但不能直接创建事实、地点、NPC、任务效果或写入事件。opening/world-evolution 审批仍校验正文泄漏、重复 ID、空 label/hint、非法 evidence quality、越界张力和非法数量；这些字段不再生成玩家入口，所有当前事实走自动揭示。

## 回合原子性

```text
Interaction
  → actionConverter
  → validate/resolve Action
  → quest / relationship / knowledge / candidate-event / ending reconciliation
  → TurnResolution
  → StateCommit
  → GameRepository.applyState(expectedRevision)
```

- 一次成功玩家回合只允许一次 `applyState` CAS；revision 成功后递增一次。
- 普通正式 NPC 回合提交同时写入 `worldState`、`storyState`、结构化事件和白名单 `PendingNarrativeJob`；prepared/rule action 直接在一次规则 CAS 中完成，active battle 延续回合只写入规则状态，不等待 AI。
- provider 场景完成后的 write-back 是独立 narrative CAS；prepared action 的场景物化与 continuation 消费则必须与规则结果共用同一次 CAS，不能混入第二次规则裁决。
- CAS 冲突不自动重放玩家选择，避免重复关系、奖励或事件。

## 修改注意事项

- 新规则先进入 ruleEngine/domain，再由 application 编排；UI/API 不裁决业务规则。
- 不从 AI narration、NPC 台词或玩家原文反推正式状态。
- 任何玩家可见选择必须有可执行 Action；任何成功 Action 必须产生结构化回合结果。
- 不新增第二个行动 endpoint、第二个 repository write 模式或兼容 use case。

## Entity 写入边界

行动规则通过 `EntityMutation` 批次修改 Entity Store，再由 projector 生成兼容字段；应用层不直接写实体数组。持久化 CAS 谓词优先于 v4 状态验证，非法实体状态零写入。NPC 的兼容 `NpcMemory` 不能与组件并行写入。
