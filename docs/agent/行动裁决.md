# 行动裁决

## 系统定位

玩家提交选择或自然语言意图，规则系统决定“能否发生、发生什么”。固定选择与自定义输入都由 `performTurn` 编排，使用同一 Action union、同一任务/关系/知识/战斗/结局规则和同一次规则 StateCommit。

## 输入边界

- 固定选择：客户端提交服务器铸造的 opaque `choiceToken`；服务端只从当前 revision 的 registry 和当前合法行动重建 choice map。
- 自定义输入：客户端提交文本与焦点 NPC ID；服务端意图解析器将其转换为受支持 Action，不能把玩家宣称当成已发生事实。
- 客户端不提交 Action、`actionKey`、规则 effect、事实 ID 或候选事件 ID。
- 请求携带 `expectedRevision` 与每次新建的 `actionId`。非法、stale、重复或已经结局的请求不能留下部分写入。

## 当前 Action 能力

- `talk`：与在场 NPC 交谈，更新结构化 NPC 记忆、关系和知识边界内的事件。
- `explore`：观察/探索当前地点并产生结构化主事件。
- `investigate`：发现当前可调查事实；Action 可携带 `approachId`，但该值只能从服务器批准的 opaque choice token 重建，客户端不能直接提交事实 ID、方式 ID、代价或后果。
- `move`：移动到相邻且已解锁地点。
- `take_item`：拾取当前地点可获得物品。
- `attack` / `battle_action`：进入或推进确定性速度队列战斗；战斗行动支持攻击、技能、防御、撤退，目标由服务端 opaque token 绑定。
- `ack_prologue`：确认序幕，只能走受批准的固定选择。
- `freeform` 是服务端自由文本解析后的受控 Action 形态，不允许绕过规则写任意 effect。

没有规则实现的公开 action 不进入 Action union，也不能在 UI 中出现“以后再实现”的死按钮。

## 调查行动裁决与自动揭示

- 有 2–3 个 `WorldFactEntry.investigationApproaches` 的当前 `discover_fact` 目标，必须通过方式 token 选择调查；缺少方式时返回 `INVESTIGATION_APPROACH_REQUIRED`，方式不存在或不属于当前事实时返回 `UNKNOWN_INVESTIGATION_APPROACH`。
- 没有已批准方式的事实不接受玩家直接 `investigate`，返回 `FACT_NOT_INVESTIGABLE`；已发现事实继续使用 `FACT_ALREADY_DISCOVERED` 拦截重复调查。
- 每个批准方式都会铸造不同的 runtime token 和语义摘要。方式的安全 `label`/`hint` 不能泄漏完整事实正文；`evidenceQuality` 只能是 `clean`/`noisy`，`tensionDelta` 由审批边界限制在 -5..20。
- `autoResolveCurrentInvestigation(worldState, storyState)` 是规则层纯辅助：当移动抵达或 NPC 交接暴露出无方式的当前 `discover_fact` 时，只返回一个自动 `fact_discovered` 结果；它不执行 quest reconciliation、不写 ledger、不创建 pending job。真正的事件、目标推进与 tension 写入仍在同一规则回合的 StateCommit 中完成，最多自动推进一个目标。
- 自动事件省略方式元数据，旧事件读取时 `evidenceQuality` 默认 `clean`、额外 `tensionDelta` 默认 0。场景生成只消费已经结算的事件和目标结果；即时场景 write-back 是独立 narrative CAS，不能再次发现事实或修改 tension。

## 调查生成、审批与 fallback 边界

AI/fixture 只能提案调查方式，不能直接创建事实、地点、NPC、任务效果或写入事件。opening/world-evolution 审批会拒绝正文泄漏、重复 ID、空 label/hint、非法 evidence quality、越界张力和非法数量；非法列表降级为空列表并记录稳定分类，未审批内容不得进入 `WorldFactEntry`。AI 不可用时由题材词库生成两个互不相同的安全方式；空列表保持无方式自动揭示。

## 回合原子性

```text
Interaction
  → actionConverter
  → validate/resolve Action
  → quest / relationship / knowledge / candidate-event / ending reconciliation
  → TurnResolution
  → StateCommit
  → GameRepository.applyState(expectedRevision)
```

- 一次成功玩家回合只允许一次 `applyState` CAS；revision 成功后递增一次。
- 普通正式 NPC 回合提交同时写入 `worldState`、`storyState`、结构化事件和白名单 `PendingNarrativeJob`；prepared/rule action 直接在一次规则 CAS 中完成，active battle 延续回合只写入规则状态，不等待 AI。
- provider 场景完成后的 write-back 是独立 narrative CAS；prepared action 的场景物化与 continuation 消费则必须与规则结果共用同一次 CAS，不能混入第二次规则裁决。
- CAS 冲突不自动重放玩家选择，避免重复关系、奖励或事件。

## 主要文件

- `src/game/domain/action.ts` — Action 与 Interaction union。
- `src/game/gameplay/rpg/ruleEngine/` — 合法性、状态转移、任务、战斗和结局。
- `src/game/gameplay/rpg/dialogue/` — NPC 自由文本的规则化关系/记忆裁决。
- `src/game/application/actionConverter.ts` — 玩家输入到 Action。
- `src/game/application/performTurn.ts` — 唯一行动 use case。
- `src/game/application/stateCommit.ts` — 单次规则提交边界。
- `src/game/application/server/persistence/gameRepository.ts` — CAS repository port。
- `src/app/api/game/actions/route.ts` — 唯一行动 route。
- `src/game/application/buildChoiceMap.ts` / `gameSessionView.ts` — 当前事实方式与 opaque token 的 read model 投影。
- `src/game/application/sceneGenerationContext.ts` / `deterministicSceneSource.ts` — 只消费调查结果的即时场景叙事。

## 修改注意事项

- 新规则先进入 ruleEngine/domain，再由 application 编排；UI/API 不裁决业务规则。
- 不从 AI narration、NPC 台词或玩家原文反推正式状态。
- 任何玩家可见选择必须有可执行 Action；任何成功 Action 必须产生结构化回合结果。
- 不新增第二个行动 endpoint、第二个 repository write 模式或兼容 use case。
