# 探索与任务推进

## 状态

Phase 4 已实现完成（2026-07-27）。玩家可以从开场地点移动到连通且已解锁的相邻地点；已发生的移动、交谈、调查会由纯规则推进受支持的主线/支线 objective；任务完成、解锁、当前地点与 revision 在同一次原子写入内持久化并可刷新恢复。

## 设计边界

- 移动、目标满足、任务完成和解锁只能由 `src/game/gameplay/rpg/` 的纯规则裁决。
- 任务完成条件来自已编译蓝图的 objective，不能由 UI、玩家文本或未来 AI 自行宣称完成。
- Phase 4 只实现 `move`、`visit_location` / `talk_to_npc` / `discover_fact` 的确定性推进；`obtain_item`、`defeat_enemy`、失败分支、结局和战斗留在后续阶段。
- UI 从 application 的当前场景 read model 得到 NPC、可移动地点、可行动列表和任务状态；不得直接读取蓝图或存档。
- 继续复用现有 revision compare-and-swap；不需要也不得修改 shared package。

## 实现记录

### 移动合法性、稳定拒绝码和事件

`move { locationId }`（`src/game/gameplay/rpg/actions/`，Phase 3 三种意图之外新增）合法当且仅当：目标地点存在于蓝图、不是当前地点、当前地点的 `connectedLocationIds` 含目标、目标在 `GameState.unlockedLocationIds` 中（隐藏地点初始锁定）。连通性只读当前地点蓝图出边，不做反向推导。

move 专属稳定拒绝码（`ValidationCode`）：

- `UNKNOWN_LOCATION` - 地点不存在（与 observe 共用）
- `LOCATION_ALREADY_CURRENT` - 已在目标地点
- `LOCATION_NOT_CONNECTED` - 当前地点与目标不连通
- `LOCATION_LOCKED` - 目标地点尚未解锁

成功移动产生 `LocationVisitedEvent { type: "location_visited", locationId, occurredAt }`，切换 `currentLocationId` 并去重登记 `visitedLocationIds`（重复到访只追加事件）。Phase 3 旧存档没有 `visitedLocationIds`：repository 读取时默认为 `[currentLocationId]`，与 `initializeGameState` 语义一致。

### objective → 状态变化、onSuccess 解锁与未支持 objective

`src/game/gameplay/rpg/quests/reconcileQuests.ts`（纯函数，quests facade 唯一导出源）在每次成功行动后核验 active 任务。objective 是状态事实的读取条件：

- `visit_location` 读 `GameState.visitedLocationIds`（含开场地点）；
- `talk_to_npc` 读 `NpcRuntimeState.met`；
- `discover_fact` 读 `WorldFactState.discovered`；
- `obtain_item` / `defeat_enemy` 在 Phase 4 未支持，永不满足——含未支持 objective 的任务保持 active，不能绕过完成（stage 2 主线即使 talk objective 已满足也不会完成）。

只有 active 任务的全部 objective 满足时才完成（追加 `quest_completed { questId, occurredAt }`），完成时按序应用 onSuccess：

- `unlock_quests`：仍为 locked 的目标任务置为 active 并追加 `quest_unlocked { questId, occurredAt }`；
- `closed`：任务终态标记为 `closed`（完成即关闭，无后续解锁，不产生 completed 状态）；
- `reach_ending`：结局判定在 Phase 4 之外，仅标记 completed，绝不伪造结局事实。

被解锁任务在同一次 reconciliation 内继续核验（固定点迭代），无迁移时原样返回输入 state（幂等）。`performAction`（`src/game/application/performAction.ts`）按严格顺序 resolveAction → reconcileQuests，把行动事件与任务事件并入同一份最终 state，恰好一次 `applyResolvedAction` compare-and-swap 写入；拒绝、陈旧 revision 或 reconciliation 抛错一律零写入。

### 当前场景/任务 read model、API 和 UI 入口

- `GameSessionView`（`src/game/application/gameSessionView.ts`）：`OpeningGameView` 演进出的语义中性会话 read model。`availableActions` 含 move（观察/交谈/调查/前往），`presentNpcs` 按运行时 NPC 位置投影（不读开场名单），`activeQuests` 只含 active 任务（locked/completed/closed 与任务 ID 不泄漏；objective 带 `completed` 与 `supported` 标记，未支持类型 `supported: false` 用中性文案）。`getCurrentGame` 与 `performAction` 均返回该视图；`OpeningGameView` 类型保留为兼容别名。
- API：`POST /api/game/actions` 严格解析 `move`（intent 字段白名单，未知字段 400）；`GET /api/game/current` 恢复同一视图。
- UI：`src/components/TravelPanel.tsx`（可前往地点）、`QuestTracker.tsx`（任务追踪）、`SceneActionPanel.tsx`（固定行动）；`CurrentGameScreen.tsx` 消费 `GameSessionView` 并在版本冲突时重新读取当前存档。
- 边界：UI/API/store 对 `actions/`、`quests/`、`scenario/` 只许门面导入，deep-import 由 `src/dependencyBoundaries.test.ts` 拦截。

### 固定 seed 探索回归与 Phase 4 未覆盖部分

`src/game/application/phase4ExplorationRegression.test.ts` 对武侠/科幻/都市三个 pin fixture 各跑真实临时 SQLite 旅程：create → move → stage 1 完成 → stage 2 解锁 → reload；验证视图内容与独立复跑管线的该类型蓝图一致、内容预算在旅程后不变、刷新恢复出与行动返回完全相同的视图，以及 stage 2 不能绕过未支持 objective 完成。

Phase 4 未覆盖的主线闭环部分：stage 2 主线无法完成（`obtain_item` 未支持）、stage 3 的 `defeat_enemy` 与结局判定、任务失败分支、物品获得与使用、战斗、隐藏地点解锁、自由文本输入与一切真实 AI 生成。
