# 探索与任务推进

## 系统定位

探索、调查、交谈、移动、拾取与战斗结果由 ruleEngine 产生结构化事件，再由任务 reconciliation 推进 objective、主线幕和可达路线。AI 文本与玩家宣称都不能直接完成任务。

## 当前规则

- `explore`：观察当前地点并产生正式 `location_explored` 类主事件。
  - 探索入口（行动栏与 AI 提案场景选项）只在当前地点存在可探索内容时投影（2026-08-10 方案 1 修订）：仍有未发现的线索事实、未满足的地点相关目标（visit_location / discover_fact），或候选事件池中有涉及当前地点的有效（未过期）候选事件。
  - **探索与实体处理分离**：探索动作不替代拾取或攻击（分别走独立 take_item / attack 入口），但场景存在未处理物品或敌人时允许先观察现场；完全没有实体或线索的地点仍不显示探索，避免空转按钮（2026-08-12 真机覆盖修复）。
  - 判定实现：`src/game/application/buildChoiceMap.ts` 导出 `hasExplorableContent(ws, ss)`；`gameSessionView` 行动栏与场景 registry 选项共用该判定。
- `investigate`：只发现当前主线 `discover_fact` 目标对应的、当前地点可调查且未发现的事实。若该事实有 2–3 个已审批 `investigationApproaches`，行动栏投影各自不泄漏正文的安全 label/hint 和独立 opaque choice token；若没有方式，则不投影调查按钮，由规则边界自动揭示（见下方 2026-08-20 小节）。调查与移动一样走即时场景写回。
- `talk`：目标 NPC 必须在场；NPC 对话会更新结构化关系/记忆，并可满足交谈目标。
- `move`：目标必须已解锁、相邻且不是当前位置；成功更新 current/visited location。
- `take_item`：物品必须存在、位于当前地点且未拥有。
- `attack` / `battle_action`：只有合法敌人与 active battle 可推进 defeat objective。
- objective 支持 visit location、talk to NPC、obtain item、discover fact、defeat enemy；完成/解锁/失败/结局只由规则事件触发。

## 2026-08-24 调查/移动与 prepared continuation

- `investigate` / `move` 走即时规则结算，并在同一次 StateCommit/CAS 中消费正式 NPC 回合已经审批的 `PreparedContinuationState` step；命中时零 live/world/provider 调用，按 post-commit revision 铸造当前 scene 的 choice token。prepared 内容缺失或图与权威事件不匹配时返回稳定 continuation 错误并零写入，绝不在动作路径转 live source 或生成 deterministic fallback。
- `take_item` / `give_item` 没有 prepared step 时是规则拥有的物品边界，写入 `source="rule"` 场景；回退到已访问非目标地点和 active battle round 同样只走规则 CAS。幕推进/结局对需要的世界演化必须在此前被允许的 opening/NPC provider job 内完成，不能由线性动作补发 provider。

## 2026-08-23 对话收尾 handoff

- 普通焦点 NPC ready scene 固定为两个对白选项；完成所需对话轮次且 objective 已推进时，同一次 scene 生成 NPC 最后一段直接回应和一个唯一 handoff choice。该 choice 是玩家承接 NPC、前往下一任务/地点/人物的真实 opaque Action，不生成第二个选项，也不以“知道了”结束。
- `gameSessionView` 将唯一 scene choice 挂到旧 NPC 的 `handoffChoice`，不重复投影到底部 `narrative.choices`；只有非焦点零回合闲聊继续使用“知道了”。

- handoff acknowledgement 是本地 UI 关闭动作：不创建 actionId、choiceToken 或 pending job，不改变 revision/turn/location，也不显示“等待 NPC”。

## 2026-08-20 调查方式与无方式事实自动揭示

- 同一地点存在多个事实时，只为当前 `discover_fact` 主线目标投影调查方式；非目标事实不进入行动栏，避免事实 × 方式把玩家入口放大成不可控列表。
- 每个批准方式都走同一个 `investigate` 规则裁决并完成同一个事实目标；`fact_discovered` 事件记录 `approachId`、`evidenceQuality`（`clean` / `noisy`）和 `tensionDelta`。不同方式的证据完整度与动静代价必须能在事件账本、StoryState tension 或结果叙事中观察到，但不能造成软锁。
- 旧事实或审批后没有方式的事实不留下空按钮。移动抵达或 NPC 交接把事实暴露为当前目标时，规则在该成功行动的 reconciliation 边界自动写入一次 `fact_discovered`，不创建额外回合或 pending job，且一次最多推进一个 `discover_fact` 目标。
- 自动揭示、玩家调查和目标推进都由规则层写入 WorldState/eventLedger；`generatePendingScene` 与即时场景 write-back 只消费已结算结果，不能重复裁决事实或修改 tension。reload 只恢复已经写入的事件，不等待不存在的调查 pending。
- AI 只能提案调查提示；opening/world-evolution 审批负责数量、重复 ID、正文泄漏、evidence quality 与张力范围校验。非法列表降级为空列表并走确定性题材 fallback，不能污染事实、地点、NPC 或任务状态。

## 原子性

- 一次成功 Action 的状态转移、任务 reconciliation、候选事件激活和 provider job 由一个 StateCommit 提交；若 action 命中 prepared step，规则结果、scene 物化、token 铸造和 continuation 消费也在该 CAS 中完成。
- `revision` 是唯一 CAS；stale/非法选择零写入且不部分完成 objective。
- 场景生成 write-back 不重新执行任务规则。

## 动态世界

- expansion 可以在任务角色/地点缺口、低张力或候选事件需要时提出新实体。
- 已有合适实体时优先 reuse；新实体通过类型、引用、预算、节奏与收束审批后才可加入世界。
- 终幕、resolution、soft/hard limit 或 budget exhausted 时停止扩张，保持主线可完成。

## 修改注意事项

- objective 只能读取 `WorldState` 已提交事实，不读取 narration 或玩家原文。
- 新任务必须有可验证 objective、解锁路径与至少一个可达结束条件。
- UI 只提交 opaque token 或 free text；不得直接提交 location/fact/quest effect。
