# 剧情连续性与结构化记忆

## 职责

本系统维护事件账本、已发布叙事原文、情节记忆与检索；主线和幕推进由任务规则负责，叙事生成由运行时 AI 负责。规则提交事件，事件账本是连续性的事实来源；`StoryState.history` 保存实际提交的 A/B 原文，`StoryState.memory` 是从完整账本确定性重建的投影，二者都不是候选正文的缓存。

## 当前契约

- 存档版本与错误分类见 [实体状态](实体与组件世界状态.md)；事件以稳定身份、顺序和引用定义，不用 WorldState 的 schema 号命名。
- `CommittedNarrativeEvent` 由 canonical commit helper 铸造，带稳定 `eventId`、`episodeId`、顺序、因果事件引用、实体/任务/事实/地点引用和 payload。规则、开局、世界增量、场景写回与战斗使用同一账本。
- `NarrativeHistory` 由 `appendHistory` 按稳定 ID 幂等追加；玩家选择/自由输入保存完整原文，实际发布的旁白、NPC 台词和展示选项按 `expressions` 顺序保存。`shown_choice` 只是展示，不是玩家言行，也不产生 Event；生成但未消费的 continuation 不进入 History。
- 场景表达式的 `audienceIds` 是实际听众。旁白只对玩家可见；同场 NPC 不会自动听见私聊，后续 NPC 只能使用在更早表达中明确披露给自己的事实。旧 `segments`/`npcLine` 字段只作为输入和 UI 兼容投影，正文权威是有序 `expressions`。
- 初始化既往事件按顺序提交 `opening_history_established`，开放问题提交 `opening_thread_established`；两者属于 `init:<generationId>` episode、turnNumber=0，并携带事实、参与者与因果引用。公开历史正文由账本和当前知识权限投影，SQLite reload 后从同一 ledger 重建，不另存一份权威摘要。
- `rebuildEpisodicMemory` 从完整 ledger 重建 episodes、recent scenes 和 NPC contacts。SQLite reload 校验 ledger 与 memory 的深度一致性。
- `retrieveNarrativeMemory` 按 required event/episode、任务或事实、实体、因果、地点、显著度和顺序稳定排序，输出有界 memory cards；近期场景是独立的有界工作上下文。
- 历史 memory cards 保留结构化事件摘要；已发布原文通过独立的 observer 记忆包提供。玩家过去的选择、自由输入、旁白和对白分别保留来源种类，不能把选择标签当作口述证言。引用只能指向已提交且权限允许的来源，secret fact 正文或其他 NPC 私密历史不因召回而公开。
- 战斗失败回滚战前 entity store、event ledger 与 History 快照，不留下失败链；胜利只提交胜利 episode 及其 cause chain。
- `StoryState` schema 12 持久化 `threads`、可为空的 `dialogueFocus`（NPC、实体和事件引用）以及 pending narrative job 的 durable attempt；开局问题会绑定真实初始化事件、任务和参与者。`advanceStoryThreads` 只消费本批已提交且与 Thread 相关的事件；空 `closure` 不会自动收束，`resolved`/`abandoned` 状态与 Quest、Goal、Promise 状态分开保存。`unresolvedThreads` 是由 `threads` 派生的兼容投影。
- `reconcileStoryConsequences` 是 A/B 共用的纯后果预览：只接收已提交或本批实际事件，按“知识变化→NPC goal→Quest/Thread→reveal/幕推进”组合既有规则，不重跑玩家 Action、不生成未来续接，也不自动选择终局。追加的 goal/quest 事件由调用方与场景事件按同一 `turnId` 顺序提交，最终一次 CAS 写入。
- 主线主动退出通过正式 `abandon_quest` 写入 `quest_abandoned`，退出终局由后续 B 生成；生成失败不回滚 A 已提交的退出事实。承诺后续会按主线 Thread 的 promise 引用在离场时释放或标记违约，任务物品不因退出自动转移。
- 开局中心 concern 只沿已绑定主线任务续接后续获批主线 ID。最终主线完成可以开放结局选择，但不会提前把该 concern 标为 resolved；实际 `ending_reached` 才提供收束依据。带显式 closure、goal、promise 或与主线无关的 Thread 仍按各自条件保留。
- `projectObserverEvidence` 先按 observer 投影 History、Event、已知 Entity；History 依据实际 speaker/audience，Event 还须满足事实权限。`shown_choice` 永远不是体验或知识，隐藏实体名和别名不参与候选排序。
- `projectStoryConsequences` 为当前请求只读投影本轮必需 Event、相关活跃 Thread、Goal 引用和已批准互动 ID；它不持久化目标正文、私密理由、证据质量或未授权条件。`projectObserverEvidence` 与 `retrieveStoryEvidence` 仍按 observer 的参与、听众和事实知情状态过滤这些来源；goal 状态事件不会自动授权其完整因果链。
- `prepareNarrativeMemory` 从有效概览、全部未覆盖原文和当前 Action/焦点构造一次 `retrieveStoryEvidence` 查询。概览/近期来源中的 Entity/Event 引用可引导有界旧话召回；当前输入、明确实体及 Thread/Promise 依据优先，已呈现原文只对可选召回去重，mandatory 依据不被数量限制截去。召回结果不再递归扩展新实体，歧义保留为候选。
- `buildNarrativeMemoryContext` 只接受投影内的来源，保存完整未覆盖原文、概览/召回原文、概览 Event 正文和 mandatory Event。事件按稳定 eventId 去重；`referencedEntityIds` 从实际使用的来源派生并与 observer 已知实体求交集，供当前 Entity 卡片查询。历史物品 owner 或地点不覆盖当前权威状态。作者/审阅使用 player 包；NPC 自知包仅送入对应角色判断，再经过现有 outward 授权。
- 当前 job 的实际 Event、活跃 Thread 的 evidence Event 和被引用的旧 History 会作为同一 bounded retrieval 的 mandatory 来源；因此原话离开近期窗口后仍可随合法证据回访/合作请求恢复。NPC 未参与、未听见或未被明确告知的事件不会进入其 memory/outward，也不能仅凭 goal 状态变化声称亲见。
- 摘要是派生缓存，不改正式存档 revision。`MemorySummaryState` 对可见有效的未覆盖 History 使用 50 条阈值、每批 10 条；当前 action/job 输入始终保留原文，不进入本次压缩。长度触发也须凑足 10 条可压缩旧原文。模型只选择已有 History/Event ID，每叶最多 4 条原文与 4 个相关事件；模型提示与解析使用同一数量限制，选编优先保留动机、约定条件、关键变化和未解决事项，超限输出拒绝而不截断；概览从全部有效叶选择对应的完整来源重新选编，最多 8 条原文与 8 个事件。生产默认概览候选来源预算为24,000估算tokens；完整请求仍受配置的输入上限约束，超限保留原文与旧水位，不保证无限历史都能压缩。批次或概览失败均不推进水位，原始 History 永远保留。
- 摘要缓存位于 `narrative_memory_summaries`，按 game/generation/observer/policy CAS 发布。读写均在同一 SQLite 事务中重新投影真实来源，验证完整叶覆盖、引用与指纹；水位只使用 History.sequence，Event 按该前缀的显式引用关联。无关尾部追加或当前 Entity 名称变化不使有效旧前缀失效；回滚、同序号不同原文和权限变化会失效。缓存损坏或失效返回 miss 并保留表头 revision，允许以旧 revision CAS 重建较低水位；有效缓存不能退水位。
- `narrative_memory_attempts` 按 job/epoch 保存固定 player/NPC 包、hash 与跨 observer 维护额度；最多 8 次摘要 HTTP、2 次批更新，请求前落盘并跨重启保留。固定包读取/冻结除自身 hash 外，还验证真实当前来源、observer、完整未覆盖原文、Event、引用与 mandatory manifest；来源变化使同 epoch 显式失败。预留/冻结核对真实 generation、pending job、epoch、候选 predicate、非空租约及有效时间；租约接管或计数变化本身不改变固定包来源。两张派生表随对应游戏清档，不进入战斗快照，不删除数据库文件。
- `BattleStartSnapshot` 同时保存 StoryThread 与 `dialogueFocus` 快照；战败或撤退恢复该快照，避免战斗失败改变开放问题或当前对话引用。
- 生产场景消费 narrative bundle；消费当前 scene 的 presented event 与规则结果同次 CAS 写入。PreparedContinuationState 仅离线 fixture。
- B 本场实际披露的知识、目标/任务后果与场景 History 在同一次有序事件追加和 CAS 中发布；审批失败不新增来源，重试不重复提交。候选后果用于本候选规则与审阅投影，不写入或替换同 job 的固定记忆包。

## 关键流程

```
规则/开局/审批结果
  → commitEventDrafts
  → rebuildEpisodicMemory
  → StoryState.history 与 memory、ledger 同次持久化
  → projectObserverEvidence
  → validate/update summary + retrieveStoryEvidence
  → buildNarrativeMemoryContext + freeze job/epoch package
  → author/reviewer player context + separate NPC private context
```

初始化 thread 会进入 `StoryState.threads`，并通过 `thread_init_*` 证据事件与首个主线任务关联；运行时按已提交事件推进其 evidence/status，终幕条件读取 Thread 派生的 unresolved 投影。系统仍不提供层级 Living Outline、真实 Arc 或分段账本；Thread 是有限的持续问题模型，不是第二份任务状态。

连续性判断仍由规则状态完成：`currentAct`、`reveal` 游标、active quest/objective、`endingAllowed` 和 evolution status 决定可见目标；记忆只提供相关历史，不改变行动裁决。

正式 composition 可注入 `memoryPreparationHooks`，按真实 observer/job/epoch 在现有同库摘要预留前记录验收额度，返回回调在本 observer 准备结束后记录实际预留与发布结果。发布依据只取 SQLite `publish` 成功返回的状态，失败批次不算发布；回调异常会阻断本次准备。此钩子不替换仓储、租约、阈值或预算裁决。
