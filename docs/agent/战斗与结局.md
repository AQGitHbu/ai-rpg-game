# 战斗与结局

## 系统定位

战斗和结局是规则系统的正式状态，不由 AI 决定。玩家只能消费当前 `GameSessionView` 下发的战斗 opaque token；ruleEngine 计算伤害、回合、胜负、任务结果和 ending 条件。

## 当前规则

- `attack` 只对当前地点合法敌人开启战斗；普通敌人按稳定 ID 组装 1–2 只，Boss 保持单体；active battle 期间只下发当前玩家单位的 battle controls。
- 角色战斗属性由规则拥有：`maxHp`、`maxEnergy`、`attack`、`defense`、`speed`；当前 HP/能量/防御状态只存在于 active battle，不参与角色成长。
- 战斗结束状态只保存上一场结果；撤退或失败后，未被击败的敌人仍可再次挑战，胜利后的敌人由 `defeatedEnemyIds` 阻止重复开战。
- `battle_action` 由速度队列逐单位结算：攻击、技能（20 能量，1.6 倍）、防御（恢复 15 能量，下一次行动前保持）和撤退；伤害为 `floor(ATK² × 倍率 / (ATK + DEF))`，防御再乘 0.5，最低 1。
- `advanceUntilPlayerDecision` 自动执行所有 rule-controlled 单位，直到下一名 player-controlled 单位或结局；每次推进最多一次 CAS，活跃战斗不创建 PendingNarrativeJob。
- 战斗开始与胜利/失败交接只消费此前正式 NPC provider job 已审批的 prepared battle step；不在 battle start 或最后一击时预热、创建 provider job 或调用 scene/world source。若不存在匹配 step，返回稳定 continuation 错误并零写入；需要下一幕或结局对的世界演化必须已在允许的 provider job 内完成。
- 场景战斗的表现按 `BattleView.units[]` 渲染任意数量的双方单位，攻击/技能按钮绑定服务端 opaque token 与具体目标；UI 只按 `lastAdvance.sequence` 展示结果，不从 HP 差推断伤害。
- 场景只渲染 HP 大于 0 的战斗单位；倒地单位保留在规则快照中用于结算与回放，但从当前战斗画面移除。
- 敌人击败、任务完成/失败、候选事件和结局解析在同一个玩家回合 StateCommit 中完成。
- 结局到达后，普通 Action 与 narrative scene 生成都停止；UI 显示结构化 ending name/description/outcome。
- `LocationSceneScreen` 在 `battle !== null` 时切换为独立全屏战斗场景：己方编队在左、敌方编队在右，旧地点背景、NPC 卡片和地点行动栏不参与战斗布局；攻击/受击位移、伤害冒字、回合反馈与战斗日志均由 `BattleView.lastAdvance` 驱动。
- 终幕立场由服务端按状态铸造：结局包的 `terminal.kind === "ending"` 契约要求 `steps` 与 `currentScene.choices` 都为空，provider 不能提交终幕选项，`approveNarrativeBundle` 也只给 `next_decision` 终点铸 registry。因此 `src/game/gameplay/rpg/narrativeBundle/endingDecision.ts` 直接从 World/Story 派生两条 `talk` 立场（`isEndingDecisionDue` + `endingDecisionStances`，抵达 NPC 取 `npcs.at(-1)`，否则取最后一名在场 NPC），`buildChoiceMap` 把它们注册为 runtime token，`gameSessionView` 经焦点 NPC 对话框下发。
- 有立场可提交时撤下「面对最终抉择」探索入口——该入口在 v7 下必然换来 `NARRATIVE_CONTINUATION_MISSING` 零写入；无人在场铸不出立场时才保留它作兜底。结局对话不开放自由输入：结局束没有任何步骤可消费自由文本。
- `resolveEnding` 优先读取最后一名终幕 NPC 的最后一次 `dialogueAct`，明确支持/质疑时分别选择信任/怀疑结局，同时保留既有亲和度条件作为其他分支的兜底。
- stale、tampered 或已消费 token 不得重复伤害、奖励、任务或结局事件。

## Plan 3 NPC 同伴连续性（已实现）

- `buildEncounter` 从统一 NPC 投影中选择 `isCompanion && active && currentLocation` 的同伴，按 NPC ID 稳定排序且最多加入一名；不增加新的玩家操作单位，仍由现有 rule controller 驱动。
- 战斗开始前的检查点包含完整 NPC Entity Components。战败或撤退恢复战前 store、事件账本和兼容投影，战斗中的 NPC dynamic/knowledge/relationship/history 变化不泄漏到永久状态。
- 只有实际参加该场战斗、最终胜利的同伴才写入有真实行动来源的 `fought_together` 关系 evidence；未参战 NPC、战败/撤退分支不获得共同作战后果。

## Prepared battle presentation

- `battle_started` 与 `battle_resolved` 是 `PreparedContinuationState` 的规则触发器，battle scene seed、结局/交接表现和后继 step 与来源 NPC 回合的 accepted proposal 一起审批。
- active battle round 仍是纯规则 fast path：每次最多一次 CAS，不创建 pending，不调用 provider。prepared battle step 的规则结算、场景物化、choice token 铸造、消费组裁剪和 revision 递增也只在一次 CAS 内完成。
- `source="generated"` 仅表示已批准 provider proposal 的 scene seed；规则拥有的导航、物品和无 AI battle presentation 使用 `source="rule"`，显式离线旅程可使用 `source="fixture"`。

## 多结局证明

- 开局世界必须提供至少两个合法 ending 定义和可达条件。
- 同 seed 的“支持”与“质疑”路线在 NPC 关系和候选事件上分化，并分别抵达 `ending_trust` 与 `ending_doubt`。
- 各分支 15+ 成功回合、三次以上 reload，重复 replay 后 world/story state 完全一致。
- 结局差异必须由结构化选择后果驱动，不能只换 ending 文案。

## 修改注意事项

- 不从 narration、NPC 台词或玩家自由文本直接设置胜负/ending。
- 新结局必须有可验证结构化条件、至少一条可达路径和分支回归。
- 结局后的请求必须稳定拒绝并零写入。
- 后续队友只需追加 `companion` combatant；resolver、CAS 和 UI 不依赖固定双方人数。

## Entity Store 与战斗回滚

战斗检查点保存完整战前 v4 `entityStore` 与 event ledger；战败或撤退时由检查点重建兼容投影，失败尝试不进入永久世界因果，NPC 五层组件一并恢复。外围 battle/ending 引用也纳入持久化实体引用校验。
