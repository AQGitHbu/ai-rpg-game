# P3 真实 API 与 UI 交接文档

## 1. 交接目的

本文件用于交接 P3 的规则模块验证，不用于评价剧情文案质量。

P3 需要证明的核心闭环是：

1. 真实 API 能生成、审阅并提交可用的剧情候选。
2. 玩家能选择调查方式并产生真实调查事实。
3. 分享事实必须绑定已发生的证据事件，不能引用未来事件或模型臆造的 eventId。
4. 玩家需要回到正确的委托人，完成核验、分享与验证。
5. 交付对象、行动、对话对象和物品状态符合规则约束。
6. 结算/立场选择使用当前 UI 暴露的 opaque token 和 revision。
7. UI 重新加载后仍能从持久化状态继续，且有可审计的完整路由证据。

不要把生成文本更顺、更像剧情或更有文学性当作 P3 的完成条件。只有当生成内容阻断上述规则闭环时，才需要调整 prompt 或审阅规则。

## 3. 为什么耗时较长，以及是否偏离目标

结论：前期确实有一部分时间被生成选项和剧情上下文牵引，但真正反复阻断 P3 的主要原因是“规则验收证据没有被正确记录或绑定”，不是剧情润色，也不是 API 额度。

每次真实交互通常会触发 provider 生成、候选审阅、规则编译和持久化提交；UI 还需要逐步打开面板、读取当前 token/revision 并提交。因此单个 action 可能耗时较长。与此同时，P3 原先的验收依赖部分由模型生成的事件 ID、当前结果证明和分享证据，导致“功能看起来发生了”但自动验收仍认为没有发生。

后续应把剧情文本视为黑盒输入，只关心：

- action 是否被规则接受；
- event ledger 是否产生真实事件；
- evidence 是否引用已发生事件；
- world/story state 是否推进；
- UI 是否使用当前 token/revision；
- reload 后是否能恢复；
- 两条 route 是否最终生成完整证据包。

## 4. 原“provider HTTP 层阻断”的澄清

此前的“provider HTTP 层阻断”描述不准确，容易让人误以为 API 服务异常。

在 `p3-live-44` 中，真实 provider 请求的运行记录均为 `output.ok: true`。之前失败批次的主要阻断是：

- `ROUTE_POLICY_NOT_EXERCISED`：动作可能提交了，但步骤记录缺少 route policy 所需的证明字段；
- 分享动作的 `evidenceEventIds` 为空，验收无法证明分享基于已发现事实；
- 模型返回了尚未发生的未来 eventId；
- ending/stance 选择没有绑定当前实际暴露的选择；
- opening 或候选审阅阶段出现未知事实、未知键或语义约束失败。

所以“API 正常”与“P3 未通过”可以同时成立：传输层成功不代表生成候选符合规则，也不代表验收证据完整。

## 5. 已完成的规则修复

以下修复均以规则闭环和证据完整性为目标，避免为了通过测试直接固定剧情文本：

- 将 `resultBoundaryProof` 从真实 action 结算结果写入 P1 step，证明调查结果、world/story state 变化和新增 event；
- P3 分享要求使用已产生的 `fact_discovered` 证据，禁止只引用未来 eventId；
- 约束证据分享/验证的事实包、受众、委托人和物理在场关系；
- 增加返回委托人、真实分享和真实验证的状态门；
- 约束 P3 调查方式与新事实产生关系，避免新 NPC 预先带入未验证的委托关系；
- 修复交互 proposal 的 NPC 在场性和 prompt 暴露条件；
- 修复 ending pair、当前立场选择和交互审阅语义；
- 修复重复分享的幂等行为；
- UI 验收继续严格使用当前 opaque token 和 revision，错误 token 会被拒绝，不允许用旧选择绕过当前步骤；
- 增加相应的 approval、candidate review、draft projection、CLI/UI journey 回归测试。

## 7. 后续最短路径

### 第一阶段：先固定当前规则基线

继续工作前先运行：

```powershell
git diff --check
npm run typecheck
npx vitest run src/game/application/approveNarrativeBundle.test.ts src/game/application/server/ai/liveNarrativeBundleSource.test.ts src/game/application/server/ai/liveNarrativeCandidateReview.test.ts src/game/application/server/ai/narrativeDraftProjection.test.ts
node --test scripts/narrativeP3Journey.node-test.mjs scripts/narrativeP3UiJourney.node-test.mjs
npm run check:docs
```

### 第二阶段：只补 UI 证据缺口

如果目标仍然是 P3 完整验收，后续只做以下事情：

1. 从当前 `p3-ui-live-01` 的停点继续，或用新的 run id 重跑 UI；不要伪造 action 14 的 token。
2. 读取当前 UI/API 暴露的 exact token 和 revision，完成 action 14、最终结算和刷新复核。
3. 保存 `private.ui-reviewed` 与 refresh proof。
4. 启动并完成 public route。
5. 生成最终 `routes.json`，确认 private/public 都是 `completed: true`。
6. 只在上述证据齐全后，才把 P3 标记为全部完成。

若 UI 继续出现 provider 生成失败，先判断是 HTTP/transport、candidate review、rule compile 还是 evidence packaging；不要笼统归类为 provider HTTP。
